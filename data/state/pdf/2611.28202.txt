Abstract
Multimodal foundation models can play video games well when the game waits for them, but
often fail when it keeps running. We find that much of this gap lies in the harness, which decides
what the model sees, what it remembers, and how its outputs become actions over time. Existing
harnesses such as VISTA improve the first two, yet turn each model call into at most one action,
so the agent acts only as often as its model thinks. We introduce AutoPILOT, which changes the
third: in each model call, the model can send a primitive action, start an open-loop macro, or
write a closed-loop controller that keeps playing from the screen without further model calls until
it hands control back. To evaluate agents in real-time games, we build AFK-Bench, 120 diverse
browser games grouped by how they respond to inaction and playable in real time or with the
clock paused. With GPT-6.1 Sol under the same budgets, AutoPILOT reaches 68.6% real-time
success against 38.3% for VISTA, and on GameWorld it keeps 80.0% in real time while VISTA
drops from 84.1% to 42.9%. Its gains hold across models, and it reaches VISTA’s final success
rate at a fifth of its API cost. Our results suggest that how a harness turns model outputs into
actions over time is a central yet underexplored part of agent design, and we hope AutoPILOT
and AFK-Bench will serve as a foundation for agents in a world that does not wait.

A harness decides what the model sees and remembers, and how its outputs become actions over
time. Prior work has mostly refined the first two [11, 12, 36, 48, 57]. The third is usually left implicit,
following the standard single-step agent loop [51] in which one model call yields at most one action and
the environment is assumed to wait for it, as in ARC-AGI-3 or game benchmarks with settings that
pause during inference [52, 54].
When the world keeps running, this default becomes a bottleneck: the agent can act only as often as
its model thinks, and on outdated frames (Fig. 1a). Letting the game clock run lowers VISTA’s success
rate on GameWorld [27] from 84.1% to 42.9%, a gap also reported by Realtime-Bench [37] and for
text-state agents [28]. Improving what the model sees and remembers does not remove it, as VISTA
performs on par with the plain Codex harness in real time despite its visual memory and inspection
tools (38.3% vs. 38.9%). Nor does more reasoning, which adds 4–7 points to VISTA at high effort.
Much of the bottleneck lies in how the harness turns model outputs into actions.
We introduce AutoPILOT, a visual agent harness that changes the third aspect by letting one model
call cover many environment steps. Like a pilot with an autopilot, the model delegates routine control
and takes over when called back. Each call chooses one of three execution modes (Fig. 1b). (1) A
primitive action is sent directly to the game. (2) An open-loop macro is a sequence of actions written
by the model. (3) A closed-loop controller is a short Python program that the model writes at run
time. It reads the screen and acts about every 0.4 s without further model calls. Control returns to the
model on a wake event: the macro or controller finishes, requests a handoff, or meets a screen it was
not written for. Both the model and its controllers see screenshots, not the game state.
To evaluate agents in real time, we introduce AFK-Bench (Away From Keyboard), 120 browser games
evenly divided into three types by what happens while the agent is idle. In hostile real-time environments,
inaction risks failure. Benign real-time environments keep changing but do not punish inaction. Turn-
based environments advance only when the agent acts. A lost game restarts within fixed budgets of
model calls, game time and environment steps. Every game can be played in real time or paused, and
the difference measures what real time costs the agent.
With the same model (GPT-6.1 Sol) and budgets, AutoPILOT succeeds in 68.6% of real-time episodes
on AFK-Bench, against 38.3% for VISTA, and in 62.5% vs. 16.7% of hostile real-time ones. Running
the clock costs AutoPILOT 4.5 points on AFK-Bench and 2.9 on GameWorld, against 17.8 and 41.2
for VISTA, and AutoPILOT leads even with the clock paused (73.1% vs. 56.1%), because one model
call can execute a whole plan. The gains hold with Claude Opus 5.5 and four further models, and
AutoPILOT uses 47% fewer tokens and reaches VISTA’s final success rate at 0.2× its API cost (Fig. 4d).

Related Work
Tab. 1 compares AutoPILOT with representative agents and harnesses, and Sec. A gives an extended
discussion.
Harnesses for visual and game agents.
Most agent harnesses follow ReAct [51], taking one action
per reasoning step. Later work changes what the model sees or which tools it may call [20, 48].
On ARC-AGI-3 [3], VISTA [11] lifts the same models to perfect scores through visual memory and
re-inspection of past frames. OpenVLHarness [57] adds visual tools and multimodal memory for static
visual reasoning. Embodied agent frameworks and harnesses let general vision-language models act
in simulated environments and control robots [6, 18, 49]. Computer-use agents [29, 46] and game
agents [35, 36, 43] also act on screenshots. Most game agents, however, pause the game while the model
generates, as do many game benchmarks [52] and the Lite setting of VideoGameBench [54]. These
harnesses improve what the model sees or remembers, but assume that the world waits for it.
Evaluation in real time.
Latency is a major reason why vision-language models fail at real-time
games [54], and recent benchmarks keep the environment running during inference [15, 37, 39, 44].
Closest to ours, The World Won’t Wait [28] compares paused and live clocks and finds that a strong
but slow model wins only when the game is paused. Its agents, however, read structured text states.
Its TORSI method still calls a model for every decision, with a slow teacher guiding a fast student.
AutoPILOT acts on pixels and instead changes what one model call can do.
Acting between model calls.
Temporally extended actions date back to options [34]. Language models
also write programs that serve as policies or skills [16, 19, 40, 41], but these programs mostly run on
structured state in environments that wait. AutoHarness [22] refines a code policy with environment
feedback and resets offline, per game and for turn-based text games. Real-time agents pair a slow

model with a fast layer: a reactive thread [44], concurrent inference coroutines [47], action chunks [4],
options held until a timer or repetition check fires [14], a scripted executor over fixed macro actions [21],
rule-based reflexes with latency charged to the simulation clock [56], or reflexes and policy trees compiled
in advance [5, 9]. Asynchronous function calling lets a returning call interrupt the model [10]. The
most similar mechanism is DPT-Agent [55], in which the model writes condition rules at run time that
steer a hand-built state machine over the symbolic state of one game. In these systems, the fast path is
mostly another model inference, code fixed in advance, or rules for a game-specific executor. AsyncLLM
can rewrite its coroutines, but only between evaluation rounds. AutoPILOT instead delegates acting
to controllers that the model writes from pixels during the episode, including their perception, and
interrupts them through wake events.
3
AutoPILOT
AutoPILOT is developed on VISTA [11], which is built on the Codex harness, with additional tools for
running macros and controllers in the background and wake events that return control to the model.
As in VISTA, the model sees rendered frames together with the game clock and its remaining budgets,
but never the game state or the DOM, from which only restart and decision-screen events are derived
(Sec. B). AutoPILOT keeps VISTA’s act tool, read-only tools (inspect, read pixels, history) and
note files, so the two harnesses expose the same tools apart from delegation. All games share the same
harness instructions and only the game description, task and controls differ. Sec. C shows the full
prompt, which adds budget rules, play tips and delegation rules to VISTA’s instructions. AutoPILOT
also reports the remaining budget after each tool result and notifies the model of restarts.
3.1
Acting in real time
At time t the agent can read a frame o(t) and send an action: one keyboard or mouse event or an
explicit wait, which counts as one environment step. The model is invoked in discrete model calls: call
k reads the frame at time tk and takes ℓk seconds, a median of 6.1 s for GPT-6.1 Sol at low effort.
Existing visual harnesses turn each model call into one action, computed from o(tk) but executed at
tk + ℓk. In real time this causes two problems: every action is ℓk seconds stale, so a projectile that was
safe in o(tk) may have arrived by then, and the agent acts at most once per model call. Pausing the
clock removes both but changes the task.
AutoPILOT instead lets a single model call act over many steps, by starting a macro or a controller
that keeps acting without further model calls. The model thus chooses how many steps each model call
covers, and its actions no longer wait for the next call.
3.2
Three execution modes
As shown in Fig. 1b, each model call may invoke one of three tools that act on the game. They differ
in how long they act without the model and whether they read the screen.
Primitive action (act). The model sends one action. act also stops any running macro or controller.
Open-loop macro (run macro). The model writes a sequence of actions, e.g. a menu route learned from
earlier interaction, and the worker sends them without looking.
Closed-loop controller (python). The model writes a short Python function run(api) that the worker
executes for up to 120 s in a sandbox with one CPU, 1 GB of memory and no network access. Sec. B
gives the full setup. It reads frames with api.observe(), decides with ordinary code, and acts with
api.act(). A controller re-reads the frame and acts about every 0.4 s with no model call. It can also
ask the model for help through a handoff, one of the wake events described in Sec. 3.3. Fig. 2 shows a
macro and a controller from two recorded episodes.
3.3
Handing control back
For delegation to be safe, control must return to the model once the running program no longer fits the
situation. While a macro or controller runs, the model’s tool call blocks: the model waits instead of

producing tokens, and the game is played by the worker. The call returns with a fresh frame on one of
six wake events:
• From the program. Handoff : the controller requests one with a reason, e.g. on reaching a goal or
seeing something it was not written for. It may keep playing while the model reads the reason.
Return: run ends at the stopping condition the model wrote or with an error. Macro done: all macro
actions are sent.
• From the harness. Decision screen: the game waits for a choice, such as in a shop. Scene change:
most of the screen differs from a second earlier and then holds still. The harness then stops the
program, since its plan may no longer fit. Timeout: the program has run for 120 s.
A game restart after a loss affects the two modes differently. It stops a running macro, which then
returns and wakes the model. It does not wake the model while a controller runs, since the controller
observes an incremented reset epoch and can keep playing. Restarts do not pause the game: the next
attempt starts at once, whether the model is thinking or a program is running. A running controller
keeps playing it, and the model learns of the failure at its next wake event, where it can reflect and
write a revised controller. After waking, the model can keep, replace or stop (with act) the running
controller. Thinking and acting overlap only after a handoff, while the controller keeps playing and the
model reads the reason. This overlap is small in practice (2.3–3.5% of inference time, Sec. F.3).

Clock protocols.
Every game can be played under two clock protocols. In real time, the game clock
never stops: the game keeps running during each model call, as for a human player who looks away
from the keyboard. Under the paused clock, the harness freezes the game from the start of each model
call until it ends, together with any running macro or controller. Game time therefore passes only
while no model call is in progress. Every game becomes turn-based for the agent, with no time pressure
while the model thinks. Under both protocols, the games’ own pause and restart controls are blocked,
so the agent cannot stop the clock itself. The drop from the paused clock to real time measures how
much an agent loses to its own latency.
Budgets.
An episode ends with a win, the game’s own end, or when one of its budgets is used up: 100
model calls, 2000 s of game time or 2000 environment steps. A model call is one invocation of the model,
which issues at most one tool call (a reply without one also counts). An environment step is one action
sent to the game, whether by act, a macro or a controller. A single-step harness thus spends one
model call per step and sends at most 100 steps, so only the call and time budgets bind it, whereas one
AutoPILOT model call can launch a macro or controller that sends many steps, and the step budget
caps these. In real time, thinking time counts as game time, while loading and automatic restarts do
not. After a loss, the game restarts within the same budgets, so the agent can try again.
Metrics.
Our main metric is the success rate (SR): the fraction of episodes in which the game’s official
success check fires before any budget is used up. Because an episode can span several attempts, SR
measures whether an agent wins within its budgets, possibly after earlier losses. Sec. 5.3 also reports
success on the first attempt. The mean progress (PG) gives a finer signal. It averages over episodes the
highest progress reached in any attempt, which the evaluator normalizes to [0, 1] for each game. We
also report the number of model calls, tokens and API cost per episode.

Experiments
We aim to answer four questions: how much a single-step harness loses when the world keeps running
and whether AutoPILOT recovers it (Sec. 5.2), where the gains come from (Sec. 5.3), how they scale

5.3
Why AutoPILOT wins
We analyze the gap in three steps: gains beyond latency, the responsible component, and recovery from
failures.
Gains beyond latency.
Even with the clock paused, where no action is stale, AutoPILOT beats VISTA
by 17.0 points with GPT-6.1 Sol and 21.7 with Claude Opus 5.5, so latency explains only part of the
gap. The rest comes from executing a whole plan per model call instead of a single action, which makes
far better use of the model-call budget. VISTA spends one model call on each action, so long action
sequences use up its budget: 208 of its 222 real-time failures end by exhausting its 100 calls, after
only 78 steps per episode. AutoPILOT instead sends 681 steps from 43 model calls, about 16 per call,
because one macro or controller carries out many steps. The model also chooses the mode that fits
the game (Tab. 3): controllers send 98% of the steps in hostile real-time and 89% in benign real-time
environments, whereas in turn-based environments, which allow planning ahead, macros account for
36% of calls and 26% of steps.

Scaling reasoning effort.
Prior work finds that slower, reasoning-heavy agents degrade in real time, as
the world moves on while the model thinks [28, 44]. In our runs, high effort hurts neither harness, but
only AutoPILOT turns it into a large gain (Fig. 5). With Claude Opus 5.5, AutoPILOT rises from
53.3% to 69.2% and VISTA from 30.0% to 36.7%. With GPT-6.1 Sol, both gain a few points (68.6% to
71.7% and 38.3% to 42.5%). At either effort, VISTA stays far below AutoPILOT at low effort, by 26.1
and 16.7 points at high effort. For AutoPILOT, a longer call yields a better program that then acts for
many steps.
Scaling generation speed.
We simulate faster or slower models with a decoding speed of v tokens/s:
the clock stops during generation and then advances by N/v s for N output tokens. On the 80 hostile
real-time and benign real-time tasks (Fig. 4c), AutoPILOT with GPT-6.1 Sol at low effort rises from
55.0% at 10 tokens/s to 63.8% at 200 tokens/s, close to the paused clock. VISTA, by contrast, reaches
38.8% even at 200 tokens/s, against 57.5% when paused. AutoPILOT stays strong even at low speed
because speed only delays when a working controller starts: once written, a controller plays at full speed
however slowly the model thinks. Slow generation hurts most when outputs are long: Claude Opus 5.5
at high effort, which writes about twice as many tokens per call as GPT-6.1 Sol, gains the most from
speed (31.3% to 62.5%, Tab. 20).
5.5
Generalization to GameWorld
We also evaluate both harnesses on GameWorld [27], whose 170 tasks in 34 browser games do not
overlap with AFK-Bench, using the same budgets (Tab. 6). With the clock paused, the two harnesses
are close (84.1% vs. 82.9% with GPT-6.1 Sol), as GameWorld tasks are short enough that VISTA rarely
runs out of calls (3 of its 27 failures). In real time, however, VISTA loses 41.2 points with GPT-6.1 Sol
and 25.9 with Claude Opus 5.5, while AutoPILOT loses only 2.9 and 4.7. The robustness of AutoPILOT
to the game clock carries over to a different set of games.

Conclusion
We presented AutoPILOT, a visual agent harness in which the model delegates acting to macros and
controllers that it writes at run time. Because each model call can launch a whole plan rather than a
single action, AutoPILOT substantially outperforms existing harnesses in real time at lower cost, across
models and on two benchmarks, without any training. Our results suggest that how model outputs
become actions over time deserves as much attention in harness design as what the model sees and
remembers, for game agents and agents operating live interfaces or robots.

Appendix
A
Extended related work
Agent harnesses.
A harness is the code around a model that turns the environment into the model’s
observations and the model’s outputs into actions. ReAct [51] interleaves reasoning with one action
per turn. SWE-agent [48] shows that the interface given to the model matters as much as the model.
CodeAct [41] lets a single action be a program that calls many tools. VISTA [11] perceives the game
as images, keeps every frame in a lossless visual memory and lets the model re-inspect frames as it
reasons, raising the ARC-AGI-3 score of the same model from 40.68 to 100. Our episodes restart after
a loss, so the model can reflect on failed attempts as in Reflexion [31].
Computer-use and game agents.
Vision-based computer-use agents ground actions in screenshots [7,
23, 29, 46]. Game agents range from reinforcement-learning policies trained per game [24] to foundation-
model agents that play many games from pixels or structured state [32, 33, 36, 40, 42, 43]. Lumine [35]
trains a vision-language model to play 3D open-world games in real time. It reads frames at 5 Hz, emits
actions at 30 Hz and reasons only when needed. It reaches real-time play through training, whereas
AutoPILOT uses a general model without training.
Real-time evaluation.
VideoGameBench [54] reports latency as a major failure cause for vision-language
models. Real-Time Reasoning Gym [44] and ROAR [39] advance their environments during inference.
Realtime-Bench [37] evaluates 30 web and 20 game tasks from screenshots under wall, paused and
token clocks with a one-action-per-model-call harness. Win Fast or Lose Slow [15] adapts model size
and quantization to the time pressure. The World Won’t Wait [28] evaluates 180 tasks from six game
types. It uses structured text observations and game-specific action interfaces. Several of these plan
ahead, such as button plans in Mario and flap schedules in Bird. While a model call is pending, the
previous control stays active.
Acting while thinking.
AgileThinker [44] runs a reactive and a planning thread in parallel, and
SwiftSage [20] pairs a small fine-tuned model with a large one, in the spirit of dual-process theories [13].
AsyncLLM [47] is a general framework for asynchronous inference rather than a game agent, and it
is evaluated mainly on streaming video understanding. In two ViZDoom scenarios, a background
thinker sets a course of action that a fast coroutine turns into per-frame actions from the two latest
frames. An appendix experiment lets the agent rewrite its own coroutines between evaluation rounds.
Real-time chunking [4] executes one action chunk of a robot policy while the next is generated. Dong et
al. [9] show that GUI agents often choose correctly but act too late. They pre-compile guarded policy
trees sized to the decoding latency, which raises success within the decision window from 0.50 to 0.79.
Their branches are enumerated in advance for discrete GUI states, whereas AutoPILOT’s model writes
closed-loop programs for continuous games at run time. TypeGo [5] runs planning loops at several
timescales and has an LLM compile reflexes offline into Python condition and action functions that run
at 100 Hz. AutoPILOT synthesizes its controllers at run time from the current screen.
B
Harness details
Tools.
Tab. 7 lists the tools available to the model in each harness. AutoPILOT keeps VISTA’s act
and read-only tools and adds run macro and python, which together give the three execution modes of
Sec. 3.2.
Actions.
Every action, whether sent by act, a macro or a controller, uses one schema. Its types are
wait, press key, press keys, type, click, click hold, mouse move, drag and scroll. The action
press key holds one key, and press keys holds two keys at once but rejects opposing directions. The
action type enters up to five characters. Each action is one environment step. Coordinates refer to the
1280 × 720 screenshot, durations are at most 2 s, and the default hold or wait is 0.4 s. Only the keys of
the game’s declared controls are allowed.

Macros.
run macro takes a list of at most 200 actions and sends them in order without reading the
screen. With the default on reset:
stop, a game restart stops the macro. With continue, the list
restarts on the new attempt.
Controller API.
A controller is a function run(api) that a background worker executes for at most
120 s. It runs in a Docker sandbox with one CPU, 1 GB of memory, 60 s of CPU time, no network and no
access to the game or host files. Python, NumPy and a run macro helper are available. api.observe()
returns the latest frame as a 720 × 1280 × 3 RGB array together with the public state: the game
clock, the remaining budgets and reset epoch. api.act(action) sends one action in the format
above, which counts as one step toward the step budget. api.request handoff(reason) wakes the
model while the controller keeps running. Returning from run ends the controller and also wakes the
model. api.notify reset(reason) records a game restart, signalled by an incremented reset epoch,
without waking the model. A new controller replaces the running one, and act stops it. There is no
fixed control rate: a controller observes and acts as fast as its own code and action durations allow. In
practice it acts about every 0.4 s.
Waiting and waking.
After a run macro or python call, the harness holds the tool result while the
macro or controller runs, so the model produces no tokens in the meantime. It polls every 0.25 s for
one of the wake events of Sec. 3.3. The result is released with a fresh frame on a handoff, when the
program ends, stops or times out, or when the episode ends.
Screen watch.
Each macro and controller has a screen watch, which raises the scene-change wake
event and which the model can tune or turn off per call. A scene change fires when at least half of the
screen differs from the frame about one second earlier and the new screen then holds for three frames,
so a flash or continuous motion does not trigger it. An optional static check fires when the screen stays
unchanged for 10 s while actions are sent. On a trigger the watch stops the program by default. It can
instead only wake the model.
Signals derived from the game state.
No harness reads the game state, but two kinds of events derived
from it reach the agent. Automatic restarts. After a loss, AutoPILOT’s controllers see an incremented
reset epoch, and the model receives a one-line notice that the attempt failed and the game restarted.
Codex receives only this notice, and VISTA receives the last frame before the restart. Decision screens.
Four of the 120 tasks, all hostile real-time, declare game states in which the game waits for a choice.
In real time, AutoPILOT and Codex poll the game state every 0.25 s. When such a screen appears,
the running controller is stopped and the model receives a neutral notice. VISTA receives no such
notice. No harness receives it with the clock paused. Removing the four tasks changes the real-time
gap between AutoPILOT and VISTA from +30.3 to +30.2 points with GPT-6.1 Sol and from +23.3 to
+21.6 with Claude Opus 5.5.

VISTA then receives its official instructions, with one added sentence in real time: “Real time continues

# Real-time play
The game keeps running while you think, call tools, and run Python.
## Budget and ending
- You have 2000 seconds of game time. Loading and automatic restarts are not counted.
- You can make at most 100 tool calls; a response without a tool call also counts as one. Actions sent by your running
controller do not count toward this limit. All game inputs together are limited to 2000.
- A response without a tool call is submitted as a final answer and the episode continues. Only the game decides
success.
## Choosing a tool
- Use ‘act‘ for single inputs: starting, quick reactions and recovery.
- Calling ‘act‘ stops a running controller.
- Use ‘run_macro‘ for a short sequence whose effect you have already seen.
- Use ‘python‘ for a controller that keeps playing from the screen while you think. Prefer ‘run_macro‘ when it is
enough.
- Test an uncertain control briefly before you rely on it for longer.
- Decide what visible change counts as progress. Motion on screen and passing time are not progress.
- Let a controller keep running while you think only if it is already working. Otherwise have it hand control back and
stop.
The Codex harness receives no instructions of ours beyond the game text and the following rules:
- The game runs in real time. It does not pause while you think or use tools.
- You have 2000 seconds of game time. Loading and automatic restarts are not counted.
- You can send at most 100 responses. Each ‘screenshot‘ or ‘act‘ call counts as one response, and so does a reply with
no tool call.
- You can send at most 2000 game inputs. Each ‘act‘ is one input, including waits.
- A reply with no tool call is submitted as a final answer and the episode continues; it also uses one game input. The
episode ends only on success, game end or budget end.
Later runs of AutoPILOT add three rules and end every tool result with a budget line such as Budget
left:
1999 of 2000 game inputs, 99 of 100 responses, 1989 of 2000 s game time.
- Each ‘act‘, each ‘run_macro‘ action and each ‘api.act‘ call uses one game input, including waits. A response without
a tool call can also use one game input. Other tools and ‘api.observe()‘ use none.
- If any budget remains, keep playing: try a different approach instead of giving a final answer.
- Combine several waits, clicks or key presses into one ‘run_macro‘ call: each tool call uses one of your 100
responses.
Later runs of Codex and VISTA add the keep-playing rule and a similar budget line. Success does not
depend on the line, as Tab. 10 shows.
D
Baselines
VISTA runs its official GameWorld profile and tools through the Codex app server of Codex CLI
0.159.2, like AutoPILOT. Its budget is 100 tool calls plus 2000 s of game time. Every tool call counts,
including inspect, read pixels, history and the note tools. The Codex harness runs Codex’s own
base instructions, agent loop and context compaction in a single thread per episode. Web search,
browser and computer use, skills, plugins and sub-agents are disabled. Its code execution has no
shell, file system or network access. The Claude Code harness runs Claude Code’s default system
prompt and agent loop with act and screenshot as its only tools. All built-in tools are disabled, and
context-compaction turns do not count as model calls. The no-op agent sends no step from the start of
an episode to its end, with the same automatic restarts and the same evaluator. Each episode runs for
600 s of game time. It wins no task. Its mean progress is .079 in hostile real-time environments and at
most .002 in the other two, consistent with the type assignment of Sec. 4. The random agent sends a
uniformly random valid step as fast as the harness allows, at a median of 2.9 steps per second. It runs
one episode per task, within 2000 steps and 2000 s. It wins 5.8% of tasks, mostly in hostile real-time
environments, where it wins 10.0%. It raises mean progress over the no-op agent by .234 on paired
tasks, so progress is best read against this floor.

E
Benchmark details
Games.
The 120 games run offline in a pinned Chromium image. Of these, 37 are built with HTML5
canvas, 21 with PICO-8, 22 with Unity WebGL, 17 with Flash through the Ruffle emulator, 13 with
Godot, 9 with other WebAssembly engines and 1 with Phaser. Each game exposes its state to the
evaluator through a small per-game adapter, which the agent cannot access. None of the 34 games of
GameWorld is among them. We collected and wrapped all 120 games ourselves from freely playable
web games. The manifest records the source page of 111 of them and pins every game file by its hash.
Of these pages, 94 are on itch.io, 10 on Armor Games, 3 on Kongregate, 3 on Newgrounds and 1 on
Not Doppler. Tab. 9 lists each game’s author, source and licence. Eight games carry a licence stated by
their author. The other 112 games state no licence, so we treat their terms as unknown.
Selection.
From a pool of 568 collected games, each game was assigned an environment type from its
description and idle probes. A task was admitted only after a scripted acceptance test that uses no
model and runs with the same code and browser image as the reported runs. Its 13 checks test whether
a scripted policy can win in real time. They also require that pausing through either harness stops the
game clock and that resuming restores normal speed. Score, prompt and screen must agree, the game
must show no undeclared freeze, and failures and restarts must be detected. Memory must stay within
its limit, and 60 s of idling must cause no penalty in turn-based games but must cause one in hostile
real-time games. The game’s own pause must be blocked, and phases the agent cannot control must be
recognized. The budget must be feasible, the prompt must name only allowed keys, and the game state
must be sampled at a regular rate. The 120 tasks were frozen before any run reported here. For games
whose danger appears only after some play, a second probe first plays a scripted policy for up to 120 s
and then idles for 60 s.
Episode rules.
All runs block the games’ own pause and restart controls. From the moment a game
reports a failure until it is playable again, all actions are discarded but still counted as steps, including
those of a running controller. This time does not count as game time, and neither does loading or an
automatic restart. Phases the agent cannot control, such as automatic cutscenes, do not count as game
time either. A wall-clock safety cap of 4000 s ends any episode. Every real-time episode is audited
against the game’s own clock for pauses. An episode is scored by the benchmark’s evaluator only. A
run that fails for infrastructure reasons is retried automatically and not scored. A used-up budget is a
failure. A model response that takes longer than the per-call deadline of 300 s, or a request that the
model provider rejects as too large, counts as a failure of the episode. Tab. 8 lists all 120 games with
their environment type and per-game results.

Other models
Both harnesses with four more models.
Tab. 2 includes VISTA and AutoPILOT with four further
models: DeepSeek-V4.1-Flash, Qwen4-Max, GLM-5.3-Flash and Hy4-flash. We access them through
OpenAI-compatible APIs and run them through the same Codex app server as GPT-6.1 Sol. The
first three think at low effort. Hy4-flash has a single thinking mode. Tab. 13 gives the paired tests.
Budgets, tasks and rules are those of the main experiments, with one episode per task and seed 42.
AutoPILOT wins more tasks than VISTA with every model. In real time its lead ranges from 13.3
points with Qwen4-Max to 29.2 points with Hy4-flash. Every comparison is significant, with exact
McNemar p ≤1.5 × 10−4. With DeepSeek-V4.1-Flash and Hy4-flash, unlike with GPT-6.1 Sol, pausing
the clock barely changes either harness. With DeepSeek-V4.1-Flash, VISTA goes from 20.0% to 24.2%
and AutoPILOT from 39.2% to 44.2%, with p = 0.30 and p = 0.21. With Hy4-flash, VISTA goes from
3.3% to 5.8% and AutoPILOT from 32.5% to 38.3%, with p = 0.25 and p = 0.17. With GPT-6.1 Sol,
by contrast, VISTA goes from 38.3% to 56.1%. With Qwen4-Max, both harnesses gain from pausing:
VISTA goes from 14.2% to 25.0% (p = 0.015) and AutoPILOT from 27.5% to 41.7% (p = 5 × 10−4).
With GLM-5.3-Flash, VISTA stays near zero at 3.3% and 1.7%, while AutoPILOT rises from 18.3% to
26.7% (p = 0.053). With all four models, the gap between the harnesses persists when the game waits,
so with these models it does not come mainly from the running clock.
GameWorld.
Tab. 14 shows these models on GameWorld in real time. With Qwen4-Max, AutoPILOT
also leads and wins 57.1% against 27.6% for VISTA. Here 53 tasks are won only by AutoPILOT and
3 only by VISTA (p = 8 × 10−13). With Hy4-flash, it wins 51.8% against 20.0%, with 54 and 0 such
tasks (p = 1 × 10−16).
Provider limits and cost.
These providers reject requests above a size limit. VISTA sends its visual
memory and AutoPILOT its recent frames with each request, so long episodes can exceed it. Such
episodes count as failures, as do responses over 300 s and paused episodes that reach the 4000 s wall-clock
safety cap. At list price, a real-time episode with Qwen4-Max costs $0.68 with VISTA and $0.49 with
AutoPILOT. With DeepSeek-V4.1-Flash it costs $0.20 and $0.23.

Who is playing when.
In the direct-API runs, a controller plays alone for 55.5% of game time, the
model thinks while no controller runs for 40.3%, and both happen at once for 1.5%, which is 3.5%
of inference time. With the Codex app server, a controller runs during 2.3% of inference time. In
hostile real-time environments the first two shares are 70.1% and 27.4%, and the overlap is 6.2% of
inference time. Of the 3,239 automatic restarts, 74% happen while a controller plays alone, 24% while
the model thinks, and 1% while both are active. A model call takes 6.1 s at the median, 10.7 s at the
75th percentile and 18.1 s at the 90th. A controller acts every 0.41 s, measured as the median interval
between its actions. Handing off while the controller keeps playing is supported but rarely used: in
83% of handoffs the controller stops within 1 s. In a variant that kept the controller running and woke
the model every 120 s, tested on 36 tasks, the share of inference time during which a controller kept
playing rose from 7.8% to 26% without more wins. It won 7 of the 36 tasks, against 8 in a standard
run on the same tasks.
Open-loop controllers.
To test whether controllers need to read the screen while they run, we run
AutoPILOT with GPT-6.1 Sol with controllers that cannot read the screen. The run uses one episode
per task with the same tasks and seed as the first main-table run. In it, api.observe() is refused,
and api.act() reports only success and game end. The model still sees the frames when it writes
a controller, so such a controller is a timed program planned in advance, like a macro with loops
and timing. Without frames, the controller has no screen watch, and its tool description is adapted
accordingly. Macros, the model’s own frames, restart notices and budgets are unchanged. Programs
that cannot read the screen at run time still win 78 of 120 tasks, against 83 for the full harness and 80
without controllers. Exact McNemar tests give p = 0.30 and p = 0.79. Against the full harness, 5 tasks
are won only by the open-loop version and 10 only by the full one. By environment type, they win 23,
25 and 30 in hostile real-time, benign real-time and turn-based environments, against 26, 23 and 34
for the full harness. Most of the gain over VISTA thus comes from delegating timed action sequences,
which macros already provide. Reading the screen at run time adds five wins, a difference that is not
significant.

Failures and restarts
How episodes end.
In real time, all 113 failed episodes of AutoPILOT end with a used-up budget:
game time in 44, steps in 42 and model calls in 27. Of VISTA’s 222 failed episodes, 208 end by
exhausting its 100 model calls and 14 end earlier, before any budget is used up. VISTA spends 544 s
of game time per episode on average and AutoPILOT 829 s. With 4000 s of game time, only 3 of
AutoPILOT’s successes come after 2000 s, and its remaining failures run out of steps in 19 episodes and
of model calls in 16, rather than of time.
Restarts.
With GPT-6.1 Sol in real time and counting every automatic restart, AutoPILOT restarts
9.1 times per episode on average and VISTA 7.9. With Claude Opus 5.5, they restart 9.3 and 5.1
times. With this count, as in Fig. 4a, AutoPILOT wins 45.3% of its 360 episodes without any restart
and VISTA 35.0%. Within 20 restarts, they reach 65.8% and 38.1%, and 54.2% and 15.8% in hostile
real-time environments. With GPT-6.1 Sol, one episode per task and three times the model calls,
VISTA rises to 55.0% overall and 37.5% in hostile real-time environments, as Tab. 19 shows. This
is still below AutoPILOT with the standard budget in the same run, at 69.2% overall and 65.0% in
hostile real-time environments. AutoPILOT itself gains little from 300 model calls and reaches 71.7%.
Lives.
Fig. 7 splits episodes into lives at each restart. A life lasts about as long under both harnesses.
Its median is 51 vs. 49 s with GPT-6.1 Sol and 55 vs. 45 s with Claude Opus 5.5. However, an
AutoPILOT life costs 2 model calls against 8 for VISTA with GPT-6.1 Sol, and 1 against 12 with
Claude Opus 5.5. After a failure, VISTA thus has fewer model calls left for the next attempt. On the
paired episodes of Fig. 7c, it used up its 100-call budget in 110 of 123 with GPT-6.1 Sol and in 29 of 37
with Claude Opus 5.5, against 5 and 4 for AutoPILOT. So after an automatic restart, AutoPILOT
still wins 58% of paired episodes against 6% for VISTA with GPT-6.1 Sol, and 30% against 11% with
Claude Opus 5.5.

Generation speed.
The study of Fig. 4c controls latency directly, and Tab. 20 gives its numbers. The
game is frozen while the model generates and then runs for L = N/v seconds for N output tokens
before the model call takes effect, with no fixed overhead. The study uses the 80 benign real-time and
hostile real-time tasks and the standard budget. Each episode is checked for timing errors and repeated
if a check fails. From v = 10 to 25, 50, 100 and 200 tokens/s, AutoPILOT succeeds in 55.0%, 56.3%,
61.3%, 63.8% and 63.8% of the 80 tasks. It wins 21, 24, 25, 24 and 25 of 40 benign real-time tasks and
23, 21, 24, 27 and 26 of 40 hostile real-time tasks. Within tasks, the odds of success grow by a factor of
1.54 per doubling of v, with p = 0.005. This estimate uses a conditional logistic regression with tasks
as strata, and 20 tasks have mixed outcomes. Pooled over tasks, a Cochran–Armitage test on log2 v
gives p = 0.15. Mean progress is .760, .762, .782, .798 and .799 and grows by .011 per doubling of v in
a least-squares fit on log2 v. Without synthetic latency, the same tasks give 61.3% with mean progress
.784, the same as at 50 tokens/s and above 25 tokens/s. This is in line with the measured speed of
about 28 tokens/s plus about 1.2 s of overhead. With the clock paused, they give 66.3% with mean
progress .821. Faster models will thus narrow but not remove the cost of thinking in real time, and
AutoPILOT already recovers most of what pausing the clock would give.

H
Limitations
AutoPILOT relies on model-written perception and control code, which is easier in 2D browser games
than in cluttered 3D scenes. In hostile real-time environments most of its wins come after a restart, so
winning an unseen real-time game at the first attempt remains open. Models also rarely let a controller
keep playing after a handoff, and doing so by default did not add wins, as Sec. F.3 reports.
