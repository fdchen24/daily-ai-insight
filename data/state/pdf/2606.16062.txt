Auditing Reward Hackability in Code RL Training
Environments
Shreshth Rajan
rajan.shreshth@gmail.com
November 2026
Abstract
Code RL rewards a policy for passing a task’s tests, so a test suite that accepts a wrong patch trains
the wrong behavior. We measure how often open code RL environments accept wrong patches and how
reliably hackable tasks can be detected and repaired, checking each claim by execution against the task’s
gold patch. First, 22.4% of 49 SWE-bench Verified tasks accept a Docker-verified patch that behaves
differently from the gold patch, and 57.8% against a stronger attacker. The gold-patch check is necessary:
an attacker not shown the gold patch returns it for 31% of its passing “exploits”. Second, across 134
public SWE-bench submissions, models pass hackable tasks 28.6 pp more often than tasks of the same
difficulty, mostly because those tasks are passable at all; pooled over three attacker runs, hackable tasks
still exceed matched passable ones (𝑝= 0.014). Third, repair is harder to verify than detection: 61.9%
of LLM-written repair tests fail on the gold patch, and even behind a gate an LLM judge is wrong on
38% of the verdicts execution can check. Finally, of 873 training trajectories behind an open coding
agent run beside the gold fix, 19.4% answer differently on a case the issue describes; an LLM review that
can only demote these executed differences judges 6.9% to be wrong fixes the tests rewarded (6.4–10.5%
across three model reviews), and 5.4% in a second public training set (R2E-Gym). Audits and repairs of
code RL environments should be decided by execution wherever execution can decide.

Introduction
Reinforcement learning from execution feedback works only when the verifier is correct. If a task’s test
suite accepts a patch that does not solve the issue, the policy is rewarded for the wrong behavior, and
reward hacking learned in production coding environments generalizes to broader misalignment [19, 29, 37].
Before committing training compute, curators need one number: what fraction of a code RL set rewards an
incorrect solution? Labs increasingly answer with LLMs. An attacker proposes test-passing wrong patches
[27, 47], a test writer hardens the suite [15, 16], and a judge decides whether a new test blocks the exploit
[32, 35].
We measure that fraction on SWE-bench Verified [13, 21] and R2E-Gym [12], repair the broken tasks, and
check every SWE-bench step by execution against the task’s gold patch. An exploit is a patch that passes the
tests and behaves differently from the gold patch, and a task is hackable if it accepts an exploit. A repair test
counts only if it passes on the gold patch and fails on the exploit; the judge’s BLOCKS verdict is its claim
that a test does this. We make three contributions:
1. Execution-verified hackability rates. 22.4% of 49 SWE-bench Verified tasks accept a patch that
behaves differently from the gold patch when Claude Sonnet 4 attacks, and 57.8% (three runs, SD 1.2
pp) when Claude Sonnet 5.5 attacks. Without the gold-patch check the first rate would read 28.6%: three
of the attacker’s 14 “hackable” tasks pass only with the gold fix. An attacker that is not shown the gold
patch returns it for 31% (28/91) of its passing “exploits” across three runs, against 4% when it is shown.
The check carries to training data: of 873 executed trajectories from the set SWE-agent-LM-32B was
fine-tuned on, 19.4% passed their tests with a patch that behaves differently from the fix on a case the
issue describes (Section 4).

Related work
Auditing benchmarks and environments. Hacker-Fixer loops [47] audit 1,968 terminal tasks with hacker,
fixer, and solver agents and find 323 hackable, confirming hacks with an LLM judge and a manual check of
49 environments; the hacks are released as Terminal Wrench [5]. BenchJack [34] finds 219 flaws in 8 classes
across 10 agent benchmarks; ABA [35] flags over a quarter of tasks in 168 benchmarks; BenchGuard [31]
targets tasks that reject correct work; SpecGuard [6] proves tasks broken before an agent runs; OpenAI’s
audit of SWE-Bench Pro estimates about 30% of tasks broken [23], after a SWE-bench Verified audit that
found at least 59.4% of 138 hard tasks reject correct solutions [22], the reverse of the error we measure.
These systems confirm exploits with LLM judges or people; we confirm them by executing them against the
gold patch on SWE-bench Verified, and report a per-task range on an RL training set (R2E-Gym) whose
exploit files allow only a declared-strategy check.
Strengthening SWE-style tests. UTBoost [41] and SWE-ABS [42] strengthen SWE-bench tests and reject
previously passing agent patches; Probe to Generate [15] keeps a generated test only if the gold patch
passes it, the gate we evaluate; Tan et al. [28], Luo et al. [18], and SWE-Bench Pro Verified [45] harden
2
tests or remediate unearned passes; Arctic-SWE [16] strengthens tests in R2E-Gym, SWE-rebench V2,
and Scale-SWE and reports training gains. PatchDiff [38], SWE-bench+ [2], and Ahmed et al. [1] show
plausible patches often diverge from gold; our probes follow PatchDiff’s differential testing. SWEPatchTest
finds only 9.21% of LLM-written test suites both accept correct patches and reject incorrect ones [17], and
failing reproduction tests are dominated by mechanical errors [8].
LLM judges and hackable environments. An LLM judge detects malicious repair patches on SWE-bench
Verified with 55.4% accuracy [30]; LLM-written rubrics and optimistic verifiers are exploited when checked
against an oracle [24, 33]; monitors are evaded during RL [4, 39]. ImpossibleBench [46], EvilGenie [9],
CATCH [36], Countdown-Code [14], and hack-verifiable environments [25, 26] build environments where
hacking is known by construction. Function-level RL pipelines validate synthetic tests against reference
solutions [11, 27, 43]. On whether leaky tests hurt training, a preregistered GRPO contrast on MBPP found
a 0.20-point held-out difference [44]; we make no training claim.
3
Method
3.1
Exploit generation
We attack 49 SWE-bench Verified tasks: the first 50 in dataset order (22 astropy, 28 django), minus
django-11206, whose gold patch did not resolve in our harness. The attacker receives the issue, the
fail-to-pass tests, and the first 30 lines of the gold patch, labeled as the fix the exploit must not be, and
proposes up to three patches that pass the tests without solving the issue. Patches with self-rated confidence
≥7/10 run through SWE-bench’s evaluation harness in the task’s image; a patch is resolving if the harness
reports the task resolved. The audit attacker is Claude Sonnet 4 (127 patches, $1.43 for the 50 sampled
tasks). We rerun the same prompt with Claude Sonnet 5.5, once as is and once with the gold excerpt
removed ($3.32). On R2E-Gym we sample 20 tasks from six repositories with seed 42; the attacker writes
full-file replacements, which R2E-Gym’s reward function scores. An R2E-Gym task is decisive if the gold
patch passes its tests and at least one attacker patch applies.
3.2
Correctness check against the gold patch
A resolving patch is an exploit only if it behaves differently from the gold patch, which we check in two
stages. Stage 1 compares the changed lines to the gold patch’s after stripping whitespace, and again after
dropping comments and rewriting a bare return None as return; a patch that matches is a false positive.
Stage 2 is executed, following PatchDiff [38]: for each task, Claude Opus 5.5 sees the issue, the gold patch,
and the unlabeled candidate patches and writes a standalone probe script that calls the changed code on
6–12 inputs, tagging each as a case the issue states or not. The probe runs in the task’s image twice on gold
(inputs whose result differs between the two runs are dropped) and once per candidate. A candidate whose
results match gold on every input is same; otherwise it differs, on an issue-stated input or only elsewhere.
A task is hackable if some resolving patch differs from gold.
3.3
Environment quality score
The environment quality score (EQS) selects tasks for repair. Each task gets EQS(𝑡) = 0.35𝑉+ 0.30 (1 −
𝐻) + 0.20 𝐹1 + 0.15 𝐷, where 𝑉is verifier discrimination over candidate patches [7], 𝐻the exploit pass rate,
𝐹1 the agreement between a semi-formal LLM judge [32] and execution, and 𝐷cross-model learnability
[3]. Tasks above 0.70 are KEEP, [0.40, 0.70] FIX, and below 0.40 DROP (38, 11, and 1 of the 50 sampled
tasks). The weights are a fixed prior, and the score is used only to select tasks for repair.

3.4
Sanity-gated repair loop
The repair loop writes tests meant to block each exploit and discards any test that fails on the gold patch.
For each FIX task, a test writer (Sonnet 4, temperature 0.3) proposes test methods that should fail on a target
exploit. The gate injects each test into the project’s own test file, applies the task’s test patch and the gold
patch, and runs the project’s runner on that test; a test that fails on the gold patch is discarded and triggers a
retry at temperature 0.7. Surviving tests go to the judge, three samples of a semi-formal protocol voting
BLOCKS or DOES_NOT_BLOCK per exploit. A task is upgraded FIX→KEEP when its score crosses
0.70. We ran the loop without the gate ($5.57), with it ($3.60), and with two ablations.
3.5
Executed ground truth for repairs
We decide every repair by running the tests. A test truly blocks an exploit if it passes on the gold patch and
fails on the exploit. A task is repaired if every exploit that differs from the gold patch is truly blocked by
some test generated for it, scored against the Docker-verified exploits. We run every judged test of all four
runs in the task’s image twice, once on the gold patch and once on its target exploit. Patches are applied
with git apply, falling back to patch –fuzz=5, and the phase reports an error if neither applies.

Hackability rates
SWE-bench Verified. Against the audit attacker, 11 of 49 tasks are hackable (22.4%; Table 1): 5 astropy
and 6 django. The attacker resolves 25 of 127 patches on 14 tasks, and three of these tasks pass only with
the gold fix: the exploits for django-11179 and django-11095 are the gold patch line for line, and the
two for django-11451 differ from it only by return None for return. Stage 2 probes the remaining
20 resolving patches on 11 tasks: 2 behave like the gold patch on every input, 18 differ, and every task
keeps at least one differing patch. The hacks are concrete: astropy-13236 skips the fix only inside the
two test functions it finds on the call stack, django-11239 sets SSL variables only for the test’s literal
file names, and django-11133 returns b’memoryview’. We also labeled the 20 patches by reading them
before probing, and the labels agree with the probes on all 20 about which patches behave like the gold
patch.
A stronger attacker finds more, consistently. With the same prompt, Sonnet 5.5 makes 28, 29, and 28 of
49 tasks hackable in three independent runs (57.8%, SD 1.2 pp), and 35 of 49 across the three; on 21.8% of
tasks (SD 3.1 pp) the difference from the gold patch appears on an input the issue states. A hackability rate
therefore describes the tests and the attacker together, and should be reported with the attacker named and
with repeated runs.

Hackable tasks have higher Pass@1, mostly because they are passable
The audit shows that tests accept wrong patches; this section asks whether models pass the affected tasks more
often, and whether that check can validate an audit. We collected per-task resolution for 134 submissions
from the SWE-bench/experiments repository. For each model 𝑚, Δ𝑚is the Pass@1 gap between flagged
and unflagged tasks, computed within each of SWE-bench Verified’s human-rated difficulty strata and
pooled across strata; a DerSimonian–Laird estimator pools Δ𝑚across models. All models are scored on the
same 49 tasks, so agreement among models is not evidence about tasks; the test that matters resamples tasks.
We draw 2,000 random flag sets matched on stratum (S), on stratum and gold-patch-size tercile (S+size),
and on stratum and whether the Sonnet 5.5 attacker resolved any patch for the task (S+passable).
Models pass the 28 tasks that Sonnet 5.5 can hack 28.6 pp more often than unflagged tasks of the same
difficulty, 130 of 134 models show a positive gap, and random flags matched on stratum or on stratum and
gold-patch size reach that gap in at most 1 of 2,000 draws (Figure 2, Table 2). Flagged tasks have a mean
Pass@1 of 63.5% across models, against 25.7% for the rest. A single RL-trained agent is too small a sample
for this test: on DeepSWE (trained on R2E-Gym), the audit’s 14 unchecked flags, the only set DeepSWE
was evaluated against, are solved 43% of the time against 29% for the rest, 𝑝= 0.53.

6
A 61.9% defect rate in LLM-augmented tests
The gate. Most LLM-written repair tests fail on the gold patch. The 11 FIX tasks include 3 false positives,
which leaves 8 hackable tasks to repair. In the gated run the gate checked 111 generated tests: 40 pass on
the gold patch, 65 fail, 3 error, and 3 were skipped, a defect rate of 61.9% over the 105 decisive checks,
those that pass or fail (Table 3). A stratified re-check of six tests that the un-gated judge had endorsed found
a concrete bug behind each failure (Table 6), such as a wrong import path, a repeated keyword argument, or
an assertion that inverts the function’s documented behavior.
The judge under execution. The judge’s BLOCKS verdicts are right about half the time, and the gate
removes the errors that are easiest to catch. We ran every judged test of the four runs on the gold patch and
on its target exploit. Of 92 BLOCKS verdicts, execution decides 61: 31 tests pass on the gold patch and fail
on the exploit, 14 fail on the gold patch, and 16 pass on both and block nothing, a precision of 0.51 (95% CI
0.39–0.63; Table 4). The remaining 31 are undecidable: 16 tests could not be injected, 7 error on gold, and
8 exploit patches do not apply. All 14 gold failures are in the un-gated run. In the gated runs, 18 of the 26
undecidable verdicts are on tests the gate skipped or that errored, which the gate passed to the judge; the
other 8 target exploit texts that do not apply. Over the 168 pairs whose test passes gold and whose exploit
applied, judge and execution agree at 𝜅= 0.41. In the three gated runs every decidable error is a test that
passes on both the gold patch and the exploit, and precision there is 0.62 (26 of 42).
Repairs and ablation. Execution confirms a small fraction of the repairs the judge claims. The un-gated
run targeted the Docker-verified exploits, so it gives the clean comparison: its judge reports 7 of the 8
hackable FIX tasks repaired, and execution confirms 1 (astropy-13236). The gated run claims 5 and
repairs 2, but its tests were written against regenerated exploit texts (below), so its executed count also
measures that failure (Table 5). Across configurations the executed count moves by at most one task; at
𝑛= 8 the ablations do not separate retry prompts or the number of judge samples.

7
Discussion
What to check. Audits and repairs should be scored against the gold patch at every step. Hackability audits
should check each exploit against the gold patch before reporting a rate: a diff catches exact copies at no
cost, and an executed probe catches the rest. Repair tests should be run on the gold patch, with an errored or
skipped check counted as a failure, and a judge’s verdict that a test blocks an exploit should be replaced by
running the test on the exploit. Patch application should fail loudly. Published hardening pipelines already
run the gold-side gate [11, 15, 47]; the attacker-side and exploit-side checks are the ones that changed our
numbers.
Limitations. R2E-Gym labels rest on each exploit’s declared strategy, since its exploit files were not stored.
The gold copies from the attacker that never saw the gold patch (28 of 91 passing patches across three runs)
may reflect memorization of SWE-bench Verified [20, 22] as much as convergence on the shortest fix. Only
the audit’s resolving patches were also read by a person (18 differing, 2 behaving like gold); none of the 179
differing Sonnet 5.5 patches were, which is why we report the issue-input rate beside the any-input rate.
Counting only patches a reader labeled as hacks, the audit’s rate is 16.3% (8/49); counting only issue-stated
inputs, 8.2%. The headline Sonnet 5.5 arm shows the attacker 30 lines of the gold patch, as a red team
with the reference would have and an RL policy would not; without it the rate is 32.0%. The SWE-bench
sample is 49 tasks from 2 of 12 repositories, the R2E-Gym sample 16 decisive tasks, and the repair loop 8
hackable tasks; the attack, test writing, and judging use one model family. Probe inputs and their issue tags
are written by an LLM, so a probe can miss a difference (the hackable counts are lower bounds for the given
attacker) and cannot prove two patches equivalent. A patch that differs from the gold patch may be a valid
alternative fix [10]; the issue-input column is the stricter reading. Each attacker run is one sample per task,

Changes from version 1. Version 1 reported 28.6% hackability on the same 49 tasks, a +14.1 pp Pass@1
gap across 134 models, and 9 of 11 tasks repaired. Version 2 adds the execution checks of Sections 3.2
