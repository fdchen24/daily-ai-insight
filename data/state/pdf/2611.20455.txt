Abstract
Code-search benchmarks show dense encoders
well ahead of BM25, yet coding agents do
well with grep. What does this dense advan-
tage measure? Existing benchmarks cannot
tell: they use curated queries, old code and a
handicapped BM25. To find out, we build RE-
POPREMIUM, a realistic repository-level code-
search benchmark. It ranks files in real reposi-
tories, with curated and raw queries in Python,
JavaScript, TypeScript, Go, Rust and Java, pull
requests from 2022 to 2026, and a preregistered
test pool over 91 repositories. Our experiments
trace the advantage to two sources: evaluation
choices that favor dense retrieval, such as split-
ting files into chunks for BM25 and counting
edited tests as relevant, and queries that lack
the code’s rare identifiers. Expanding the query
with LLM-written identifiers (generate-then-
grep) helps BM25 far more than dense retrieval,
letting it match dense retrieval in every Python
pool, even on pull requests opened after the
LLM was released. No method we tried pre-
dicts which retriever will win on a given query.
From these results we derive three guidelines:
measure dense gains against a fair lexical base-
line, fuse dense retrieval with BM25, and add
the code’s words to queries that lack them.

Introduction
Coding agents are tested on ever newer repository
tasks (Zhang et al., 2025; Huang et al., 2026), but
an end-to-end score does not say whether search,
reasoning or editing failed. Retrieval benchmarks
test search alone. On them, code-specialized en-
coders beat BM25 by wide nDCG@10 margins
(Kryvosheieva et al., 2025; Li et al., 2025). Yet one
practitioner report found that embeddings were not
the bottleneck for a SWE-bench agent that searched
with grep and find (Chen and Flaherty, 2025).
Teams build embedding indexes because of bench-
*Work done at Ant Group.
mark gaps, so the conflict matters. What does the
dense advantage buy, and where does it come from?
Existing evidence cannot settle this. Embedding
benchmarks mostly pair curated or docstring-style
queries with old code (Husain et al., 2019; Muen-
nighoff et al., 2023); agent reports use raw issue
or pull-request (PR) text (Jimenez et al., 2024).
Lexical baselines often reuse the dense retriever’s
chunking. Weak baselines are a known source
of false gains in neural ranking (Lin, 2018; Yang
et al., 2019; Kamphuis et al., 2020), but their effect
in repository code search has not been measured.
Gold labels also differ. SWE-bench’s gold patches
contain no test files (Jimenez et al., 2024). A PR’s
list of changed files does, and those tests count as
relevant unless they are removed. Our own first ver-
sion kept them. Tests can be fair targets elsewhere,
so we report both label rules. Finally, benchmark
code predates the encoders’ training cutoffs, so the
advantage could also reflect contamination (Magar
and Schwartz, 2022; Sainz et al., 2023).
To answer this, we build REPOPREMIUM, a real-
istic repository-level code-search benchmark over
real repositories with file-level labels. Repository
localization pipelines rank files first, and file
labels come straight from the merged change
(Section 3). Within each repository we fix the code
snapshot, the label rule and the protocol, and vary
only where the query comes from and when the
change was made. The core has 1,265 queries over
ten SWE-bench Verified repositories: curated prob-
lem statements (OpenAI, 2024) and raw GitHub PR
text from 2022, 2023 and 2026.1 Each main analy-
sis is thus repeated across query sources and years.
An extension set adds five languages, nine held-
out repositories and a 91-repository preregistered

We call dense retrieval’s nDCG@10 lead over
BM25 the dense premium and ask three questions.
How large is it under one consistent protocol?
Which queries carry it? Should a system route
each query to a retriever or fix one setup? Hybrid
retrieval is known to help (Thakur et al., 2021), and
LLM query expansion helps both BM25 and dense
retrieval (Wang et al., 2023a; Gao et al., 2023). We
use them as controlled interventions, asking which
retriever expansion helps and why, and test our
advice on preregistered held-out repositories.
We evaluate thirteen dense encoders, plus
SPLADE (Formal et al., 2021) and ColBERTv2
(Santhanam et al., 2022). Our experiments identify
where the premium comes from:
F1 Evaluation choices inflate the dense advan-
tage; a smaller lead survives on raw queries.
Indexing whole files for BM25 cuts the curated
premium from +0.121 to +0.034; counting edited
tests as relevant doubles the RAW-POST premium
(Figure 1, Section 5.1). Against whole-file BM25
the encoder still leads the raw pools, mostly
through Recall@10; on curated queries its inter-
val covers zero.
F2 Adding the code’s words closes what re-
mains.
The premium sits on queries that lack
the code’s rare words, and LLM-written identifiers
help BM25 far more than the encoder. From the
same expanded query the encoder gains a fraction
of what BM25 gains, and prose stripped of iden-
tifiers changes nothing. BM25 then matches or
beats dense retrieval in every Python pool, even on
PRs newer than the LLM. The LLM may know the
repository, so this replaces the premium but does
not explain it (Sections 5.2 and 5.4).
F3 The two retrievers win different queries,
and nothing we tried predicts which. Classifiers,
LLM judges and a preregistered router all fail. A
fixed fusion of the two beats either retriever alone
and held on 539 preregistered lockbox queries (Sec-
tions 5.3 and 5.6).
From these findings we derive three guidelines
for code search:
G1 Measure dense gains against a fair lexical
baseline. Index whole files for BM25, strip tem-
plated PR text, and state which edited files count as
relevant before comparing against dense retrieval.
G2 Keep dense retrieval and fuse it with BM25.
A fixed rank fusion beats dense alone on devel-
opment data and on 539 lockbox queries, and no
router beat the fusion. In agents, the LLM matters
more than the search tool (Section 5.7).
G3 When a query names no code, add the code’s
words before searching. One LLM call that drafts
the missing identifiers lets whole-file BM25 match
an embedding index. The call recurs per query, so
it suits repositories searched rarely (Section E).

Related Work
Agent suites such as SWE-bench (Jimenez et al.,
2024) and DeepSWE (Huang et al., 2026) run
the whole agent loop. Code-retrieval benchmarks
such as CoIR (Li et al., 2025) pair docstring- or
web-style queries with old code. None of them
varies query mining and training-cutoff date to-
gether. Their labels also differ: SWE-bench gold
patches contain no tests, while a PR’s file list keeps
every edited file. It is well known that lexical and
dense retrievers fail on different queries and that
fusing them helps (Cormack et al., 2009; Thakur
et al., 2021). Our τ is the highest inverse document
2
frequency (IDF) among tokens shared by the query
and the first source file the change edited. We com-
pute IDF over the repository’s chunks. It adapts the
MaxIDF predictor (Hauff et al., 2008) but needs
the gold file; its proxy bτ uses the query alone. LLM
query expansion helps BM25 (Wang et al., 2023a)
and, through generated pseudo-documents, dense
retrieval (Gao et al., 2023). We use it as a con-
trolled intervention, not as a proposed method. The
closest work, SWE-Explore (Zhang et al., 2026a),
also isolates retrieval: it scores the code regions
that successful agents read, under a line budget,
and its dense baseline uses static word embeddings.
We score the files the change edited, use current
code encoders, and vary the lexical baseline, the
label rule and the query source. Section A gives
further references.

REPOPREMIUM Construction
3.1
Task and Data
Task.
REPOPREMIUM is file retrieval inside one
repository. Input: a natural-language description
of a code change (an issue statement or a PR’s title
and body) and a pinned snapshot of its repository.
Output: a ranking of the snapshot’s files. Rele-
vant: the non-test source files the described change
edited. Test files stay in the ranking but count as
non-relevant, and every retriever ranks the same
files for the same query (an example in Figure 2).

Why rank whole files, not functions or lines?
Repository-level work starts by choosing which
files to edit: an engineer or an agent opens a few
files and edits within them. Localization pipelines
rank files before functions or lines (Xia et al., 2024;
Chen et al., 2025). SWE-bench’s retrieval baseline
ranks whole files with BM25 (Jimenez et al., 2024).
Bug localization has long ranked files against bug
reports (Zhou et al., 2012). Finer-grained work
ranks functions or line regions (Reddy et al., 2026;
Zhang et al., 2026a). File labels also come straight

3.2
Construction Pipeline
Six steps build the REPOPREMIUM-CORE pools
(Figure 3). The REPOPREMIUM-EXT pools reuse
the label rule and, for raw PR text, the filters and
stripper (Steps 3–5), but index their own reposito-
ries; the appendix details each pool and its results.
Step 1: Repositories.
The core uses ten of the
twelve SWE-bench Verified repositories; the other
two have too few merged PRs. RAW-POST covers
nine, as sphinx merged too few in 2026.
Step 2: Queries.
CUR-PRE takes each SWE-
bench Verified issue statement. The raw pools take
the title and body of merged PRs from each date
window, most recent first (up to 100 per repository,
40 for RAW-PRE’23).
Step 3: Gold labels.
The gold set is the indexed
source files the change edited, each with binary
relevance. CUR-PRE reads them from the SWE-
bench gold patch, which has no tests. For raw
PRs we drop edited tests and unindexed files (doc-
umentation, changelogs) from the changed-file list,
matching SWE-bench’s oracle files. Because this
choice moves the premium, we also score with tests
included (Section B.3).
Step 4: Quality filter.
A query is kept if it has
one to three gold files and every one exists at the
snapshot; a change that creates its source file is
dropped rather than relabeled. Raw PRs must also
describe a code change (at least 100 characters, at
most 20 edited files, not docs-, CI- or test-only). Of
2,733 candidates, 1,265 remain (Table 5): changes
that edit a few existing source files.
Step 5: Preprocessing.
A regex stripper removes
PR templates, checklists and HTML comments that
otherwise swamp BM25 (Sections D.1 and J).
Step 6: Corpus.
Each repository is pinned at the
base commit of its most recent SWE-bench Veri-
fied instance, and every .py file is one document;
RAW-PRE’23 uses a 2024-Q1 snapshot. RAW-
POST’s queries and changes therefore postdate
the encoders, but the indexed code does not. Re-
scoring each task at its own base commit moves no
tuned premium by more than 0.025 (Section B.2).
Further construction details are in Section B.
Release.
We release the queries, file-level labels
with a test-file flag, pinned commits, the stripper
and all evaluation harnesses (Section G).

Results and Analysis
5.1
How Large Is the Premium?
Chunking decides the sign; whole-file BM25
removes most of the gap.
On django, dense
retrieval over whole files loses to BM25 (∆=
−0.153) because the encoders truncate long files;
chunking at c = 1,000 flips this to +0.119. BM25,
in contrast, gains from larger windows. Against
whole-file BM25 the premium falls to +0.034 on
CUR-PRE and +0.059 to +0.125 on the raw pools
(Table 2). No encoder keeps a significant premium
on CUR-PRE or RAW-POST, and seven of thir-
teen fall significantly below zero on CUR-PRE (Ta-
5
ble 15). BM25’s setting was picked on the evalu-
ation queries, so these are lower bounds for dense
retrieval.
Counting test files as relevant inflates the pre-
mium.
Dense retrievers rank a test file first far
more often than BM25 (59% against 34% of cu-
rated queries). Adding edited tests to the gold sets
therefore raises the tuned premium from +0.034 to
+0.165 on CUR-PRE and from +0.059 to +0.136
on RAW-POST (Section B.3). With either rule ap-
plied to every pool, the curated and raw pools are
indistinguishable. Mixing the rules, as happens
when SWE-bench gold patches are scored next to
PR file lists, widens the RAW-POST-minus-CUR-
PRE gap from +0.025 to +0.102.
What survives is mostly coverage.
Dense re-
trieval places more gold files in its top 10 (Re-
call@10 +0.10 to +0.19) but ranks its first hit sig-
nificantly higher only on RAW-PRE’22 (Table 11).
Outside Python, a modest premium remains on
TypeScript and Rust but not on Go (single reposi-
tories; Section B.6).
Much of the reported premium thus comes from
the setup. Against whole-file BM25 the curated
premium nearly vanishes (+0.121 →+0.034),
and the raw premiums shrink by a third to over
a half. Counting test files as relevant inflates it
again. What survives is mostly wider coverage.
5.2
Supplying the Missing Evidence
If the premium reflects lexical evidence a query
lacks, supplying that evidence should help BM25
more than dense retrieval.
Generate-then-grep catches up with dense re-
trieval.
A generator (qwen35-122B, temperature
0, one frozen prompt) reads the stripped query, but
never gold paths or patches. It writes identifiers,
file and module hints, APIs, error terms and a code
skeleton, and we prepend this text to the query for
BM25. With BM25 over whole files in both arms,
generation adds 0.11–0.19 nDCG@10 to BM25,
and generate-then-grep is never behind the canon-
ical encoder. It leads significantly on CUR-PRE,
by 0.081. Its lead on the raw pools is 0.054–0.062,
but those intervals cover zero, so a small dense
lead remains possible (Table 2). Whole files are
not needed: with BM25 at the encoder’s 1,000-
character chunks, the premium after expansion is
−0.052 to +0.012.

helps the encoder far less. Generated identifiers
can replace the premium. Since the generator may
know the repository, this does not show where the
premium comes from.

5.6
Predicting the Winning Retriever
The headroom is real.
BM25 strictly beats dense
retrieval on 24% of CUR-PRE and 21% of RAW-
POST queries, and a per-query oracle would add
about 0.09 nDCG@10 over dense alone.
No classifier or LLM judge we tried finds those
queries.
We tried classifiers on structural query
features, logistic regression on query embeddings
and two zero-shot LLM judges (qwen35-122B,
gemma-4-31B-it). All reach AUROC 0.47–0.54,
with every interval covering 0.5 (Table 19). Once
tuned, each falls back to (nearly) always choosing
dense; untuned, the judges pick keyword search
for most queries and lose over 0.1 nDCG@10. The
RAW-POST intervals are wide (n = 132), so a
modest signal on raw queries cannot be excluded
(Section P).
BM25 thus wins about a quarter of queries, but
nothing we tried can tell which ones from the query.
5.7
The Agent Boundary
Swapping the search tool changes little; swap-
ping the LLM changes a lot.
With the LLM
fixed, a SWE-agent on the held-out pool (96 tasks)
scores within about 0.04 exact-match whether it
gets an unrestricted shell with grep, a lexical index,
a dense index or a bτ-router. Exact-match means the
files its final diff edits equal the gold set. Across
four setups of three LLMs on a 30-task subset,
exact-match ranges from 0.03 to 0.30. No tests
are run, so this measures localization, not fix cor-
rectness. All runs use clean environments with the
merged fix unreachable (Sections Q and Q.2).
For agents, then, the choice of LLM matters far
more for localization than the search tool it calls.
6
Discussion and Conclusion
Reconciling the debate.
Benchmark gaps and
agent experience can both be right. Against BM25
with the dense retriever’s chunking, or with edited
tests counted as relevant, dense encoders lead by
0.1–0.2 nDCG@10. Against whole-file BM25 on
source-file labels they lead by little, mostly in cov-
erage. Where they still lead, the query names no
rare identifier. A language model can add those
identifiers, and grep-style search then matches the
encoder. An agent that picks its own search terms
does the same. Fusing the two retrievers still beats
either alone (Table 3).
Guidelines.
G1 Measure dense gains against a
fair lexical baseline: whole files for BM25, tem-
plated PR text stripped, and one stated rule for
which edited files count as relevant, applied to ev-
ery query source. Report Recall@10 and an anchor-
augmented BM25 arm next to the dense number.
G2 Keep dense retrieval and fuse it with whole-file
BM25; per-query routing did not beat the fusion.
If the caller is an agent, spend on the model be-
fore the search endpoint.
G3 When a query lacks
the code’s vocabulary, add LLM-written anchors
before searching. The call recurs per query, so a
8
dense index is cheaper for repositories searched
often (Section E).
We release REPOPREMIUM with source and test
labels, the PR-boilerplate stripper, and the genera-
tion and agent-evaluation harnesses.
Limitations
The core covers ten Python repositories and the
cross-language PR pools one repository per lan-
guage, so modest effects cannot be excluded.
BM25 was tuned on the evaluation queries, gener-
ation results depend on the generator, and labels
are the files one change edited. Function- and line-
level targets are untested.

A
Extended Related Work
Benchmarks.
Agent suites refresh or harden
SWE-bench (Zhang et al., 2025; Deng et al., 2025;
Huang et al., 2026; Merrill et al., 2026) but score
the whole agent loop, so they cannot attribute a fail-
ure to retrieval. Code-retrieval benchmarks (Husain
et al., 2019; Huang et al., 2021; Lu et al., 2021; Li
et al., 2025; Xue et al., 2026a) use docstring, web or
competition queries rather than repository changes.
SWE-Explore (Zhang et al., 2026a) labels the line
regions that successful agents read. Its explanation
of why lexical search fails on issue text matches
what τ measures: the issue names no rare identi-
fier of the edited module. Our encoders descend
from code pretraining (Feng et al., 2020; Guo et al.,
2021, 2022; Wang et al., 2023b); the canonical one
is jina-code (Kryvosheieva et al., 2025).
Retrieval
methods.
Fusion,
dense,
late-
interaction, learned-sparse and cascaded pipelines
combine lexical and dense signals (Cormack et al.,
2009; Karpukhin et al., 2020; Khattab and Zaharia,
2020; Santhanam et al., 2022; Formal et al., 2021;
Lin et al., 2021; Lin and Ma, 2021; Campese
et al., 2024); we ask when the dense signal adds
value and whether that can be predicted per
query. τ builds on pre-retrieval query-performance
prediction (Cronen-Townsend et al., 2002; He
and Ounis, 2004; Hauff et al., 2008; Carmel and
Yom-Tov, 2010; Zhou and Croft, 2007; Arabzadeh
et al., 2021). LLM query expansion helps BM25
and dense retrieval (Jagerman et al., 2023; Mackie
et al., 2023; Wang et al., 2023a; Gao et al., 2023);
we use it as a controlled intervention against
pseudo-relevance feedback (Lavrenko and Croft,
2001). LLM systems outside code also rewrite a
user request into search queries before retrieving,
for example over a knowledge base and a web
search engine (Xue et al., 2023). Rerankers trained
on general web data transfer imperfectly to new
domains (Xue et al., 2026b); our reranker baseline
(jina-reranker-v3) is such a general-purpose
model.
Embeddings beyond code.
A survey of omni-
modal embeddings (Zhang et al., 2026b) organizes
cross-modal unification around coverage, compa-
rability and compositionality. Domain-specific re-
trieval also requires careful evaluation: ZooClaw-
FashionSigLIP2 (Xue and Xu, 2026) studies adap-
tation to fashion retrieval and structural biases in
benchmark ground truth. These broader settings
motivate examining how benchmark construction
shapes measured retrieval gains; our experiments
isolate this question for repository code search.
Practice and contamination.
The claim we test
is that embeddings were not the bottleneck for a
grep-driven SWE-bench agent (Chen and Flaherty,
2025); code-graph systems argue for structural re-
trieval instead (Abdelaziz et al., 2021). Contam-
ination work (Magar and Schwartz, 2022; Sainz
et al., 2023) motivates our post-cutoff pools and
the exposure test of generation.
B
Benchmark Construction Details
The construction keeps the pools comparable. Ev-
ery pool uses one corpus snapshot per repository
and one label rule (the indexed, non-test files a
change edited), and every raw pool uses the same
text filters. The checks below show that the snap-
shot, unlabeled relevant files and BM25’s tokenizer
do not drive the results, but the test-file rule does.
B.1
Construction Details by Step
These notes add to Steps 1–6 of Section 3.2 only
what the main text omits.
Repositories.
SWE-bench Verified’s 500 in-
stances cover twelve repositories; seaborn and
flask are too small for raw pools, leaving ten
with enough merged PRs in every window. The
core is Python because SWE-bench Verified is;
Multi-SWE-bench enters as an REPOPREMIUM-
EXT pool (Section L), since its Python split repack-
ages SWE-bench Verified.
Mining and labels.
Raw PRs come from the
GitHub search API, most recent first, capped at 100
per repository (40 for RAW-PRE’23); the query is
the PR title and body. Gold files come from the
SWE-bench gold patch (CUR-PRE) or the PR’s
changed-file list (raw pools). The gold patch has
no tests. PR file lists, by contrast, include tests,
documentation, changelogs and configuration files,
so scored gold sets keep only indexed, non-test files
(Section B.3). The release flags each edited file as
source, test or non-indexed. In the raw pools, tests
are 29–33% of edited files and appear in 58–63%
of queries. Unindexed documentation, changel-
ogs and templates are 29–32% and appear in about
half of queries. RAW-PRE’22 was added because
RAW-PRE’23, mined at 40 PRs per repository, is
small.

Filtering.
Filters apply in the order of Table 5.
The gold rule asks for one to three scored gold
files, all present at the snapshot, so changes that
add their source file are excluded. Edited tests and
documentation do not count toward the cap and
need not exist. The cap keeps the task a localization
problem. The text rule drops bodies under 100
characters, PRs touching more than 20 files and
docs-, CI- or test-only changes. Paths under src/X
map to X when only the latter exists. Analyses that
needed new retrieval runs use the 461 raw queries
of the original, stricter rule. The queries added by
the unified rule have a lower premium at c = 1,000,
but no detectable difference in the tuned premium
or the generation comparison. sphinx yields no
RAW-POST query: it merged ten PRs in the 2026
window.
Preprocessing.
Raw PR descriptions carry ticket
headers, checklists, AI-disclosure sections, check-
box lines and HTML comments; unstripped, BM25
on django RAW-POST collapses to nDCG@10=
0.010. The stripper (Section J) shortens raw queries
by about 40% and curated statements by about 4%.
Corpus.
Each repository is pinned at the base
commit of its most recent SWE-bench Verified in-
stance, so every CUR-PRE base commit precedes
the snapshot. The corpus is every .py file, tests
included (Table 6). RAW-PRE’23 uses a 2024-Q1
snapshot. As a result, most curated fixes are al-
ready in the snapshot, and the RAW-POST changes
come about three years after the indexed code.
“Post-cutoff” therefore describes the query and the
change but not the code. Section B.2 tests whether
this matters.
B.2
Per-Task Pre-Change Snapshots
The shared snapshot does not drive the premium.
We re-score 933 core queries at each task’s own
base commit (834 commits). Retrieval is other-
wise identical, and a guard reproduces the shared-
snapshot results exactly. No tuned premium moves
by more than 0.025, and the raw-minus-curated
gap is unchanged (Table 7). The curated premium
rises slightly, so a snapshot that already contains
the fix favors BM25 a little on curated queries.
B.3
Label Definition and the Test-File Bias
Counting edited test files as relevant rewards a habit
of dense retrievers, not localization. If one rule
is used for all pools, either source files only or
all edited files, the curated and raw premiums are
indistinguishable. Only mixing the two separates
them (Table 8).
Rule.
A file is a test if its path contains a test di-
rectory (test, tests, testing, __tests__, ...)
or its name matches a test pattern (test_*.py,
conftest.py, *_test.go, *.spec.ts, ...); it is
indexed if the pool’s corpus indexes its extension.
Every analysis is re-scored from stored top-10 lists
with these files removed from the gold set; retrieved
tests then count as non-relevant.
Dense retrievers rank tests first far more often.
Dense retrieval puts a test file first for 59% of cu-
rated and 28–35% of raw queries, against 34% and
12–16% for tuned BM25. Word overlap and file
names do not explain this: those tests share fewer
query words than the source files dense retrieval
ranks, and few are named after a gold module. Re-
production code in the query strengthens the pref-
erence, but it remains when the query has no code.
Beyond code.
Many relevance labels are har-
vested from records made for other purposes, such
as a change’s file list, a ticket’s links or a clinical
note’s codes. The harvesting rule then decides what
counts as relevant, and retriever families may differ
in how easily they find the extra items. A retrieval
comparison is only as consistent as its label rule.
B.4
Audit of Unlabeled Retrieved Files
Missing labels lower both retrievers’ scores about
equally, so they do not explain the premium. An
LLM judge (qwen35-122B) read each change de-
scription together with the top-3 non-gold files
from the canonical encoder and from whole-file
BM25. One gold file per query was mixed in with-
out its label. We used all 132 original RAW-POST
queries and 132 sampled CUR-PRE queries. The
judge marked 75–78% of gold files as files to edit,
but only 5–6% of the non-test misses, with no
difference between the retrievers. The dense re-
triever’s apparent surplus of editable misses comes
from its preference for tests (Section B.3).
B.5
Which Part of the Expansion Matters
Generation works through the identifiers it writes.
We append one group of generated fields at a time
(Table 9). Identifiers, APIs and error terms close
the premium with or without file paths, and the
code skeleton nearly does. Prose search phrases
help only through the identifiers they contain; with
those removed, the premium stays where it was.

D
Extended Findings
Three results support the main text. BM25 is usable
on raw text only after PR templates are stripped.
The τ-effect is weak per query but large across
query groups, and it is exploratory. Under one
label definition, the query pools are hard to tell
apart.
D.1
PR-Boilerplate Stripping Recovers BM25
Templates break BM25 but not dense retrieval, so
queries taken from PRs or issues must be stripped.
On raw RAW-POST queries stripping roughly
halves the premium (+0.369 to +0.175), entirely
through BM25 gains. Without stripping, BM25
on django returns the same template-matching
files (global_settings.py, docs/conf.py) for
almost every query. The repeated headers, check-
lists and HTML comments dominate BM25’s IDF-
weighted query, while the encoder largely ignores
them. A hand audit of eight stripped queries con-
firms that titles and substantive prose survive.
D.2
The τ-Effect in Detail
τ predicts how large the premium is for a group of
queries, not for a single query, and the evidence for
it is exploratory.
τ is MaxIDF on the tokens a query shares with
its target.
τ(q) (equation (1)) is the MaxIDF pre-
dictor of Hauff et al. (2008) restricted to tokens
shared with the first indexed, non-test gold file. We
chose it among four variants because it transfers
best across slices (Table 13); that choice was made
on the same slices. Its query-only analogue bτ car-
ries little per-query signal.
The premium falls with τ in both cells.
Pooled
quartile means fall monotonically, from +0.217 to
+0.050; the raw cell decays more steeply, and the
curated cell has one interior wobble.
The association is weak per query but large per
group.
The τ quartile explains about 2% of per-
query variance, as much as knowing the repository;
most of that variance is metric noise. Yet the drop
from the lowest to the highest quartile is as large as
the whole spread of the premium across encoders.
τ thus shows where the premium is but cannot route
single queries (Section P).
D.3
Query Source and Vintage in Detail
Under one label rule the core pools are not distin-
guishable, vintage has no consistent effect, and the
raw-PR premium recurs in other languages.
The pooled curated–raw gap was mostly a la-
bel contrast.
With source-file labels the raw-

E
Generation and Anchor Ablation
This appendix gives details for the two query inter-
ventions of Section 5.2 and Section 5.4; the tables
below hold the numbers.
Setup.
One generator (qwen35-122B, tempera-
ture 0, one frozen prompt) reads only the stripped
query, never gold paths or patch content. It writes
identifiers, file and module hints, APIs, error terms
and a code skeleton, which we prepend to the query
for BM25. A control arm reproduces the cached
BM25 exactly.
Generation does more than tuning BM25.
The
anchors help BM25 more than any chunk size does.
Over whole files, generate-then-grep matches the
canonical encoder on every raw pool and beats it
on curated queries (Table 2). The residuals cover
zero but are not shown to be equivalent to zero. We
therefore say that the premium is removed, but not
that the two retrievers are equal.
The anchors carry evidence, not just more text.
Corpus-based expansion (RM3) lowers BM25
rather than raising it. Embedding the expanded
query helps the encoder far less than it helps BM25,
and SPLADE and ColBERTv2 gain less from the
same anchors (Table 12, Table 10). What helps is
specific identifiers that a lexical index can match
exactly.
A stronger encoder does not change the pic-
ture.
Qwen3-Embedding-8B keeps a larger pre-
mium over the tuned BM25 on the raw pools, but
generate-then-grep again matches or beats it in ev-
ery pool (Table 10).
The size of the effect depends on the genera-
tor.
Across five generators from 4B to 122B the
direction always holds, but only the largest turns
the curated premium negative. gemma-4-31B-it
and deepseek-v4-flash close about 80% of it;
Qwen3-8B closes a little over half against the canon-
ical encoder and about two thirds against the en-
coder built from its own weights.
Memorization does not explain it.
Generation
also removes the premium on post-cutoff PRs that
appear in no benchmark, and the effect survives
when every file reference is stripped from the an-
chors.
On held-out PRs opened after the gen-
erator’s release (116 queries, seven repositories),
generate-then-grep still beats dense retrieval, with
an interval that excludes zero. Naming the gold
file is not needed either. The generator names it
more often for curated than for raw queries, yet
RAW-PRE’22 closes its whole premium although
the gold file is named for only half its queries.
Generation is cheaper for rarely searched repos-
itories.
One Qwen3-8B call takes about 1.5 s per
query. The dense index needs a one-off encod-
ing pass per repository (about four minutes for
django). Generation is therefore cheaper below
roughly 158 queries per repository. Failed genera-
tions fall back to the original query, which biases
against generation.
Removing anchors hurts both retrievers.
We
replace the five rarest tokens a query shares with its
gold file by synthetic strings of the same length and
case pattern. The placebo replaces the same num-
ber of equally rare tokens absent from the gold file,
and a guard arm reproduces the cached baseline ex-
actly. If dense retrieval matched meaning without
those tokens, its premium should rise. On curated
and raw Python queries it does not: both retriev-
ers lose a third to almost half of their nDCG@10,
by similar amounts. The premium does rise on
TypeScript, and on Rust without a resolved inter-
val. Most replaced tokens are ordinary words rather
than identifiers. Our attempt at meaning-preserving
substitutes failed its fidelity check. The edit thus
rules out matching that ignores these tokens, but
it cannot tell the loss of anchors apart from a loss

Chunk-Size and τ-Definition Ablations
Chunk size decides the baseline. BM25 keeps im-
proving up to whole files while the encoder does
not, so the common c = 1,000 protocol favors
dense retrieval. Against BM25 at its own best size,
no encoder keeps a significant premium. Among τ
variants, MaxIDF is the most informative; whole-
query predictors carry no signal.
BM25 needs large windows; the encoder does
not.
BM25 rises with chunk size: it levels off
from c = 4,000 on CUR-PRE and peaks at whole
files on RAW-POST. The canonical encoder stays
flat because it already truncates long inputs (Ta-
ble 14). Only the canonical encoder was swept.
Rebasing removes every significant premium.
Scored against BM25 at its best size, no encoder
of thirteen keeps a significantly positive premium
on either pool, and seven fall significantly below
zero on CUR-PRE (Table 15). BM25’s size was
picked on the evaluation queries, so these rebased
premiums are lower bounds for dense retrieval.
MaxIDF is the most informative τ.
Of four
shared-token variants, MaxIDF has the largest gap
between the lowest and highest τ quartile and trans-
fers best across slices (Section N). Query length
and gold-set size carry no signal, so what matters
is restricting τ to tokens shared with the target file
(Table 13).

The Behavior-Only Probe (DESC)
DESC holds 125 queries (87 from CUR-PRE,
38 from RAW-POST, all ten repositories).
For
each, gemma-4-31B-it (temperature 0) rewrote the
source query as a one- or two-sentence description
of the behavior, with every identifier, path, error
string and ticket reference removed. Gold files
come from the source query. Because a full de-
scription shrinks to a sentence or two, DESC re-
moves much more than anchors. We use it only as
one slice of the decay analysis (Section N) and as
an anchor-removal test that also loses other query
content (Section E).

Curated Multilingual Queries
Curated issue-symptom statements keep the dense
premium but lose its τ-dependence: they share rare
tokens with the target file as often as raw PRs do,
yet those tokens rarely anchor BM25. The τ-effect
is therefore specific to lexically anchored queries.
Setup.
We score 134 human-verified Multi-
SWE-bench issue statements on vuejs/core,
mui/material-ui and tokio-rs/tokio against
the same corpora, with two encoders.
The premium stays; the slope disappears.
The
premium is +0.03 to +0.18, but its pooled slope
on τ is flat (+0.002, against −0.164 for the raw
language slices).
Rare shared tokens no longer anchor BM25.
These queries have the same τ as raw PRs. Yet
three quarters return no grep hit in the top ten,
against 40% for raw PRs, and BM25 scores far
lower (Table 16).
Samples are small, query type is confounded
with language, and tokio does not show the gap.
We read this as a limit on scope, not a falsification.

N
Premium Decay across Slices
(Exploratory)
Across 38 evaluation slices the premium falls with
τ in all but one, and one common slope fits them.
Because the predictor and its normalization were
chosen on these slices, this is exploratory; a pre-
registered test on held-out repositories had the pre-
dicted sign but missed its criterion.
Model and slices.
We fit the premium as one
common function of τ’s within-repository per-
centile (IDF is not comparable across corpora) plus
a per-slice offset. The slices cover the five Python
mining regimes, all thirteen encoders on CUR-PRE
and RAW-POST, the held-out pool and four other
languages (9,339 query–slice observations).
One slope fits all slices.
The per-slice slope is
negative in 37 of 38 slices. Encoders sharing a
pool are not independent, so the fairer count is
nine of ten distinct query pools; the exception,
RAW-PRE’23, is small and near zero. The com-
mon slope is −0.165 nDCG@10 across the full per-
centile range; intervals resample repositories, then
tasks, so encoders sharing a task move together.
Dropping any one repository barely changes the
slope. A homogeneity test does not reject a single
slope. Per-slice slopes are noisy, so we make the
claim for the pooled data only (Figure 5).
The preregistered held-out test was not met.
We applied the frozen predictor to the 29 reposito-
ries of the matched replication (Section O) that no
slice used. The slope is negative in all seven sub-
slices (−0.109 pooled), but its interval includes
zero.
With about ten tasks per repository, the
within-repository percentile is too coarse to resolve
a slope of this size.

A Matched Replication at Scale
Holding the change fixed, raw PR wording raises
the premium over a curated rewrite of the same
change, for two encoders from different families. A
date effect of similar size cannot be excluded, and
the curated premium itself depends on the encoder.
Design.
We mine 360 PRs from 36 repositories in
Go, Java, Python, Rust and TypeScript/JavaScript,
five before and five after the encoders’ cutoffs per
repository; 351 keep an indexed, non-test gold file
and are scored. Each task is queried twice, against
one gold set and one corpus at its base commit:
once with the raw PR text and once with a curated
rewrite. qwen35-122B wrote the rewrite from the
PR text without seeing gold paths or patches, and
a separate call to the same model checked its fi-
delity. The curated view is thus an LLM rewrite,
not human curation. A repository-disjoint develop-
ment/test split was frozen before analysis.
Wording moves the premium within a task.
Raw wording raises the premium for both
jina-code-0.5b and Qwen3-Embedding-0.6B, in
about 70% of repositories and on the held-out test
split (Table 18). Both views share one gold set,
so the label rule cannot create this contrast. This
is our strongest evidence that wording moves the
premium; the pooled ten-repository comparison
no longer separates curated from raw pools once
labels are consistent (Section D.3).
Only the raw premium survives a change of en-
coder.
The canonical encoder keeps a premium
on both views, but the second encoder’s curated
premium is indistinguishable from zero, as it is on
never-mined DeepSWE descriptions (Section R).
This is what we expect if the premium is a property
of the query.
Date is not separated from wording.
The post-
minus-pre contrast points the way contamination
predicts and is about half the size of the wording
effect. Its interval includes zero, and a direct com-
parison of the two sizes does not separate them. By
language, all ten estimates point the same way, but
only Python (and, for the second encoder, Type-
Script/JavaScript and Rust) excludes zero on its
own. We therefore do not claim a five-language
replication.

Agent-Driven End-to-End Evaluation
Retrieval quality does not decide agent localiza-
tion. For a SWE-agent on the held-out pool, the
choice of LLM moves exact-match far more than
the choice of search tool. Our first version of this
evaluation was invalid because the merged fix was
reachable through git; all numbers here come from
the clean rerun.
Setup.
We draw stratified samples from the held-
out pool (Section B.7), balanced across its nine
repositories: 30 queries for the model comparison
and a nesting draw of 96 for the search-tool com-
parison. The agent is mini-swe-agent (Princeton
NLP, 2025) in its raw-shell configuration (temper-
ature 0, 30 steps, 900 s per query). It sees the raw
problem statement and is scored on the files its final
diff touches against the gold files: precision, recall,
any-hit (at least one gold file) and exact-match (the
gold set exactly).
The model matters most.
Across four open-
weight configurations (Table 20), exact-match
ranges from 0.033 (gemma-4-31B-it) to 0.300
(kimi-k3). Turning off qwen35-122B’s reasoning
phase changes exact-match by an amount we can-
not resolve, so the data do not show that thinking
helps. The spread across families mixes family
with scale: it shows that the served model matters,
but not why. Low-recall trajectories share one fail-
ure: the agent commits to a wrong file early and
keeps editing it.
Q.1
Search Tools at a Fixed LLM
At a fixed LLM the search tool barely matters: four
very different tools land within about 0.04 exact-
match of each other, and no difference between
them is resolved.
Design.
We fix the LLM (qwen35-122B, thinking
on) and replace the shell’s search with one tool,
repo_search. Its backend is BM25, the canonical
dense encoder, or a router that uses bτ to pick one
of the two per query. The restriction is enforced:
find, grep, rg and git grep are shadowed on
PATH, and attempts around them are logged.
No tool wins.

Q.2
Task-Environment Contamination
Our first version of this evaluation leaked the an-
swer, and the leak reversed its main result. We
report it because the mistake is easy to make in any
benchmark built from merged changes.
What went wrong.
Tasks were materialized with
git worktree add at the base commit. This pins
the files but shares the object store, so the merged
fix stayed reachable through git log --all or git
show. In 8 of 30 shell trajectories the agent read a
later commit covering the whole gold set. The tool
restriction was also only a request in the prompt,
which the agent ignored in most trajectories.
The fix, and what it changed.
Each task is now
exported with git archive into a fresh repository
with one synthetic commit and no remotes, checked
per query. The tool restriction is enforced, and the
shell has no network access; this also closes the
route by which one query had fetched its own pull-
request diff. Raw-shell exact-match fell from 0.333
to 0.133, while the BM25 tool, which had nothing
to gain from the leak, stayed at 0.167. The apparent
advantage of the shell was therefore the leak.
Limitations.
The model comparison uses 30
queries, so only its largest differences resolve. Scor-
ing is file-level: any-hit is a lenient ceiling and no
execution-based check is run. The search tools
return 20 chunk hits that are not deduplicated to
files.
R
Never-Mined Queries (DeepSWE)
DeepSWE task descriptions are written to specify
work, not mined from a completed change. On
them the premium does not transfer and BM25
wins far more often, which fits the view that the
premium depends on how queries are written.
Setup.
109 of DeepSWE’s 113 tasks pass our
qrel audit (88 repositories, five languages: Python,
JavaScript, TypeScript, Go and Rust). The gold
files are those of one reference patch, so we mea-
sure reference-edit localization rather than exhaus-
tive relevance. The retrieval harness is that of Sec-
tion 4.
The premium does not transfer.
The canonical
encoder’s premium, +0.121 and +0.152 on our
curated and raw pools, is not distinguishable from
zero here, and Qwen3-Embedding-0.6B falls below
BM25 (Table 22). This is the sharpest limit on the
premium we found, and it matches the within-task
wording effect of Section O.
Lexical rescue is a property of the query.
BM25 strictly wins 38–52% of queries, against
about a fifth to a quarter on our pools, and the two
encoders’ BM25-win sets largely coincide.
Corpus size does not explain it.
If anything the
premium shrinks as corpora grow, though no size
tercile resolves.
