An intervention that improves one agent can break another, and adding a stronger harness on top need not
repair the damage. Agent interventions such as skills, harnesses, and extra inference budget are nonetheless
usually credited with one average gain, measured under one setup. We ask instead when each intervention
helps and which failure it repairs. A matched factorial study over nine benchmarks, four models, four skill
conditions, four harness levels, and three budgets, with nearly 0.9 million trajectories, changes one axis
at a time. No configuration is best everywhere, interventions interact rather than add, and a harness can
absorb a skill’s gain, rescue a failure the skill causes, or leave the gain intact. The failure left by the current
system points to the fix: missing knowledge to a stronger model, execution errors to a richer harness. Yet
feedback is not recovery: a matched recovery repairs mainly failures that leave a visible error signal. Skills
that evolve from the agent’s own experience hit a bottleneck: they rarely beat a short human-written skill,
can learn dataset shortcuts, break when moved to another model, and cannot supply missing facts, which
outside information does. A benchmark-level switch to the model favored by a 20-task labeled pilot achieves
both higher performance and lower cost than always using the stronger model. Agent interventions should
be judged by which failure they repair and under which configuration.

1. Introduction
Can a skill built for one model break another? A skill optimized for score on Qwen3.5-9B was transferred,
unchanged, to a stronger model. On Hotpot Context, that model answers 62.0% of questions correctly without
the skill and 13.6% with it. A stronger harness that feeds back errors and allows a revision does not repair
it: the score stays at 12.2. The model still knows the answer. In 74.1% of its responses with the skill a
correct answer is present, against 76.8% without, but the skill makes the model fill its answer field with a
fact-extraction worksheet instead of the answer. The intervention did not add a capability. It interacted with a
model it was not built for and with an answer interface that the harness enforces.
This case is not an anomaly. Modern agents wrap a language model in a stack of interventions: reusable
skills [35], tool interfaces and execution feedback [40, 44], reflection and revision [23, 33], extra inference
budget [34], and, increasingly, skills that the agent evolves from its own trajectories [25, 42]. Each new
intervention is reported as a gain under its authors’ model, harness, and budget. Agent benchmarks score the
stack as a whole [20, 21, 45]. Neither tells us whether a gain belongs to the intervention, which failure it

We therefore ask: when does an intervention help, and which failure does it repair? Answering this
requires changing one intervention at a time on the same task instances. We build a matched factorial matrix
over task instance, model, skill, harness, and budget (Section 2): 1,872 test instances from nine benchmarks,
four models, four skill conditions (no skill, a one-shot self-generated skill, and two self-evolving methods,
all built by the same model and frozen before testing), four harness levels, and three budgets, each cell run
three times. The matrix contains nearly 0.9 million trajectories. The study supports four groups of findings,
summarized in Figure 1.
• When interventions help (Section 3). No configuration is best everywhere, and interventions interact rather
than add. Even with the model fixed, a harness can absorb a skill’s gain, rescue a failure the skill causes, or
leave the gain intact: an 18-word SQuAD skill adds 66.2 points under a minimal harness and 2.2 under
execution feedback.
• Which failure they repair (Section 4). The failure left by the current system points to the fix, but feedback is
not recovery: a matched recovery repairs mainly failures that leave a visible error signal.
• Where self-evolution stalls (Section 5). Skills evolved from the agent’s own experience rarely beat a short
human-written skill, can learn dataset shortcuts, break when moved to another model (the opening case),
and cannot supply missing facts.
• How to choose an intervention (Section 6). Choosing per task does not pay: neither a router nor escalation
on failure signals beats a simple fixed configuration. Choosing per benchmark does: a small labeled pilot
beats always switching to a stronger model at lower cost.

a model effect, a skill effect, and a harness effect alone. Letting each pair of axes interact instead predicts
held-out cells better on seven of eight benchmarks (mean leave-one-cell-out 𝑅2 from 0.729 to 0.812; paired
sign-flip 𝑝= 0.0078; Appendix Figure 8). Appendix D.3 gives the fitting procedure and the test.

Finding 1: Intervention value is conditional
No configuration is best everywhere, and interventions interact rather than add. A harness can absorb a
skill’s gain, rescue a failure the skill causes, or leave the gain intact, so a skill gain reported without its
harness cannot be interpreted.

Feedback is not recovery.
A matched recovery helps only if the failure travels the whole way from exposure
to a correct final answer: the error must be exposed to the model, the model must act on it, the fix must work
locally, and the repaired run must end correct. These stages break in different places. For Qwen3.5-9B at H2,
BigCode exposes an error in 70–76% of executions, yet the model repairs at most 2% of them, because coarse
test verdicts do not point to a fix. Spreadsheet repairs about two thirds of the errors it responds to, but only
about one fifth of those runs end correct, because a local fix rarely makes the whole workbook right. Across
the four models, H2 rescues 27.1% of the Hotpot FullWiki failures that were visible, actionable, and locally
correctable, but only 1.3% of such failures on Spreadsheet.

To test this within each benchmark and without using H2 outcomes, we

error, or no error signal. Failures with a signal are rescued far more often on SQuAD (76.9% versus 1.3%),
Hotpot Context (63.5% versus 1.8%), and Hotpot FullWiki (24.2% versus 1.5%), and modestly more often on
Spreadsheet (21.5% versus 17.4%). BigCode’s signals are visible but rarely acted on, and UCSB SOP shows
no difference. On SQuAD, 98.7% of H2 rescues come from interface violations, so recovery there is almost
entirely format repair. Appendix E gives the recovery-stage and signal tables.
Finding 2: The failure points to the fix, but feedback is not recovery
Missing knowledge calls for a stronger model, and execution errors call for a richer harness. Even a
matched recovery repairs a failure only when the error is exposed, the model can act on it, and the
repair survives to the final answer; it succeeds mainly when the failure leaves a visible signal.
5. Where Self-Evolving Skills Stall
Self-evolving skills promise to improve an agent from its own experience without changing the model or the
harness. The matched design shows four ways in which they fall short, and three experiments test why.
Four shortfalls.

written initial skill on five of seven benchmarks, and on the test split that initial skill also beats SkillOpt by
10–15 points on three QA benchmarks. The few human-written lines are also cheap: where the gate kept
them, they add a median 4% tokens, whereas the evolved 2,603-word LiveMath skill adds 195% (Figure 4).

short human-written skill that asks the model to request facts it does not recall removes most wrong guesses
but cannot raise accuracy on its own. When each request is answered with passages from the cited sources,
the same model reaches 60.0%, and 72.0% when the passages come with every question (Table 5d).

Finding 3: Self-evolution needs something from outside the agent
Skills evolved from the agent’s own experience rarely beat a short human-written skill, can learn dataset
shortcuts, break when moved to another model, and cannot supply missing facts. A stronger constructor
does not fix this; guidance or information from outside the agent’s experience does.
6. How to Choose an Intervention
Two policies that did not pay.
If the failure points to the fix, a controller could choose the intervention per
task. A router that chooses an action from the task text, or from a predicted failure type, does not beat the
fixed Trace2Skill+H2 configuration (39.42% and 40.10% against 45.29%), although an oracle that chooses
on one repeat and is scored on the others shows that headroom exists (49.24%). Behavior before recovery
does predict which Qwen3.5-9B H1 failures H2 will rescue (AUROC 0.945, against 0.796 for benchmark
identity), but escalating only H1 failures reaches 42.1% against 41.6% for always using H2: it cuts regressions
from 2.20 to 0.87 per 100 instances yet costs 68% more tokens, because H1 must run first. The failure state is
informative, but a policy that turns it into accuracy or cost gains remains open. Appendices E and F give the
methods and offline replays.
A policy that does pay.
The failure signal is too sparse to choose per task online. Escalating Qwen3.5-
9B+H2 to a stronger model only when its trajectory ends in a visible error, an abstention, or an over-long
answer adds about one point, because 89% of its failures at H2 are silent: the signalled ones were already
retried inside H2 (Appendix F.4, Table 50). Choosing per benchmark from a small labeled pilot works.
Running Qwen3.5-9B+H2 and a stronger model on 20 labeled tasks, and switching the whole benchmark
only if the stronger model scores higher on them, reaches 57.4 against 53.5 for always using GPT-5.6-sol, at
36% lower cost, because the stronger model is worse on some benchmark–skill combinations (on SQuAD,
for example; Appendix F.4, Table 51). The same pilot gains nothing over always using H2 rather than H1,
and matches always using H3 at 10% lower cost. Configuration dependence, which makes an average gain
misleading, is what a benchmark-level pilot exploits (Appendix F.4).
Finding 4: Choose the intervention per benchmark, not per task
Per-task signals are too sparse to choose an intervention online: most residual failures at H2 are silent.
A small labeled pilot per benchmark works: 20 labeled tasks are enough to keep the stronger model
only where it helps, scoring higher than always switching at 36–42% lower cost.
7. Discussion
A diagnostic checklist.
The findings do not yield a universal ranking, but they do yield an order of questions
to ask before choosing an intervention (Figure 6). Each step rests on a result above.
1. Fix the configuration and read the residual failures, not the average gain. A skill gain measured at one
harness does not survive another (Table 3), so the question is what still fails under the model, harness, and
budget that will be deployed.
2. Is the answer or capability missing? Factual, reasoning, and abstention failures respond to a stronger
model (+64.54 points over the other axes) or to outside information (SimpleQA: 5.0% to 60.0%), not to a
skill built from the agent’s own experience.

Limits.
Skill construction. Main-matrix skills are built by Qwen3.5-9B and reused unchanged, so the
cross-model results, including the opening collapse, test transfer rather than construction by each model; the
stronger constructor is tested on two benchmarks only. Model scope. The skill–harness regimes, the signal
coding, and the pre-recovery prediction use Qwen3.5-9B, and rescue appears only for it. Feedback versus
retry. H2 bundles error feedback with up to three retries, so their contributions are not separated. Failure
labels. Only 56.5% of source failures are labeled, the labels are validated at the level of the intervention axis,

8. Related Work
Evaluating agents.
Agent benchmarks compare model backbones under fixed scaffolds [20, 21, 45], and
HAL evaluates models, scaffolds, and benchmarks jointly [13]. Others fix the task and vary the agent’s visible
context [39] or simulated user [14], or check tool actions against executable task contracts [2]. We vary one
intervention at a time on the same task instances and repeats, so each effect is paired and attributed to one axis.
Skills and harnesses.
SkillsBench compares no-skill, curated, and self-generated skills across model–
harness configurations [18]; SkillLearnBench scores skill generation on the skill, the trajectory, and the
outcome [49]; Shaposhnikov et al. [32] evaluate about 500 skills across 19 agent–model configurations; and
Ding et al. [6] survey skill evolution and evaluation. Other work builds skill libraries [31], routes among
skills [38], and learns the harness from experience [11]; added components can also over-privilege a skill
[17] or break agent behavior [15, 16]. We evaluate self-evolving methods rather than only curated or one-shot
skills, and link each effect, gain or loss, to the failure it acts on.
Feedback, recovery, and asking.
Intrinsic self-correction often fails without external feedback [10], works
best with reliable feedback [12], and depends on feedback quality in code [26] and in time-series agents [46].
Agents can also learn when to ask an expert [41] or a patient [7]. We add stage-wise recovery evidence across
benchmarks, and show that when knowledge is missing, evolving skills from the agent’s own experience cannot
repair the failure: the agent guesses, so the missing information must come from outside that experience.
Allocation and failure diagnosis.
LLM routers choose which model answers a query [5, 9, 27], or reweight
a model ensemble over several turns [3], and compute-optimal scaling allocates test-time computation by
difficulty [34]; we instead fix the model and choose which intervention to apply. Prior work diagnoses
why agent systems fail [4], when a failure can be caught [47], and whether a change to an agent is safe to
deploy [48]; we test whether such diagnoses select the fix, and compare per-task with per-benchmark choice:
switching models per benchmark from a small labeled pilot beats always using the stronger model, at lower
cost.
9. Conclusion
We asked when an agent intervention helps and which failure it repairs, using a matched factorial study that
changes one axis at a time over nine benchmarks and four models. The answer is conditional but not arbitrary.
No configuration is best everywhere, and interventions interact rather than add. The failure left by the current
system points to the axis with room to help, and feedback repairs mainly failures that leave a visible signal.
Skills evolved from the agent’s own experience stall unless guidance or information comes from outside that
experience. Finally, the choice of intervention pays off per benchmark rather than per task: a small labeled
pilot that keeps the stronger model only where it helps beats always using that model, at lower cost.
How to judge an intervention.
The same skill can be worth 66 points or 2, and the same feedback can
repair a failure on one benchmark and none on another. An intervention should therefore be judged not by its
average gain, but by which failure it repairs and under which configuration. Self-evolving methods should be
compared against a short human-written skill and tested beyond the model they were built on, and an agent

that learns from its own experience should also learn when that experience is insufficient and where to look
[1, 29, 30, 36].
Contributions.
Beyond the four findings, this work contributes:
• A matched factorial protocol that changes one intervention at a time on the same task instances and repeats,
so every reported gain is paired and attributed to one axis (Section 2).
• A failure-to-fix analysis: failure labels frozen before any matched outcome is inspected, validated by an
independent judge and an author check, and replayed under each axis (Section 4).
• A diagnostic checklist that turns the findings into questions a practitioner can ask of a system’s residual
failures before choosing an intervention (Figure 6).
• Reusable assets: the instance-level outcome ledger for all trajectories, the frozen skill artifacts with their
hashes, the frozen failure labels with the validation sample, the split identifiers, and the scripts that regenerate
every table and figure. A new intervention can be run on the same instances and compared, pair by pair,
with every existing cell, without re-running the matrix.

sources, sample counts, split identifiers, and the train, method-validation, harness-validation, and test partition.

Ethics Statement
This work evaluates existing language models on public benchmarks and collects no human-subject or
personal data; the SOP suites describe operational procedures rather than personal records. We report null
and negative results, including that most failures are beyond every tested action, that evolved skills can break a
working system when moved to another model, and that the tested routing and escalation policies do not beat
a fixed configuration. The frozen skills derive from one model’s trajectories, so reusing them elsewhere may
transfer that model’s idiosyncrasies. Capability-boundary estimates are specific to the tested configurations
and should not be read as evidence that any failure is intrinsically unfixable.
AI Use Statement
Language models are the object of study: every evaluated configuration is a model execution, the Direct,
SkillOpt, and Trace2Skill skills are model-generated, GPT-6-sol serves as an independent judge for label
validation, and an LLM assistant proposed labels that an author reviewed in the label check. The authors also
used AI assistants for code implementation, prose editing, and checking numerical consistency. All reported
numbers were verified against the saved run artifacts, and the authors take responsibility for the content.

A.1.3
Harness (𝐻)
A Harness changes the information and actions available during execution rather than supplying a reusable
task policy. Table 1 defines the four levels; Table 11 gives their implementation on every benchmark. H1
targets interface and answer-contract compatibility, whereas H2 jointly changes failure observability and the
opportunity to act on it, so an H2 gain cannot be attributed separately to error exposure or retry. H3 tests
whether one additional outcome-blind revision improves a completed response or trajectory.
On single-turn QA, H1 adds the answer interface, H2 re-asks only when that interface is not satisfied,
and H3 always adds one revision pass that can change the answer. On SQuAD, for example, the H2
message is: “The answer interface was empty or invalid. Return one concise context-supported span inside
<answer>...</answer>.”
A.1.4
Budget (𝐵)
Low, Medium, and High ceilings are crossed only with H1 and H2; H0–H3 are also evaluated under each
benchmark’s historical Default configuration, which is not relabeled Medium. The sweep jointly raises
completion-token, turn, and timeout ceilings (Table 12), so its effects cannot be attributed to tokens alone;
these are resource allowances, not observed consumption or reasoning-effort settings. Historical UCSB Low
restricts workflow feasibility; the separately recorded protocol-preserving corrected Low reduces only the
token cap and retains its reference turns, tools, and timeout, so the two endpoints are not interchangeable.

Matched intervention and root-cause protocol.
For each intervention, we compare matched task-instance–
model configurations while changing one axis and holding the rest of the execution condition fixed. For the
failure analysis, we assign 2,225 failed source executions to eight root-cause categories using the earliest
decisive cause supported by the trajectory; Table 33 defines those categories. The source label is frozen
before matched target outcomes are inspected. Benchmark-specific deterministic checks support the label
when possible; cases requiring additional interpretation use an AgentRx-inspired constraint-grounded judge.
Two properties of this labeling limit what it can support. The judge is Qwen3.5-9B, which is also one of the
four evaluated models and the model whose training executions produced every SkillOpt and Trace2Skill
artifact, so on one quarter of the matrix it attributes causes to its own failures. Only the 305 LiveMath labels
come from this judge (Appendix D.4.1), and an independent judge does not reproduce them, so LiveMath is
excluded from every root-conditioned analysis; Appendix D.4.2 reports the independent-judge and author
validations of the remaining labels. We therefore treat model-assisted labels as hypotheses throughout and
mark them as such in every table; Section D.4 gives the definitions and the evidence boundary.
Measurement validity.
An unchanged-configuration repeat comparison (A/A) compares repeated executions
of the same task instance to measure variation without an intervention. Noise-qualified improvement must
exceed the corresponding A/A tolerance, whereas success requires reaching the benchmark’s native success
threshold. Section A.6 distinguishes these criteria and documents label coverage, budget limits, and the
calibration status of the reported descriptive results.

Repeat design.
We use three repeated executions per cell to capture material execution-level nondeterminism.
In a controlled Spreadsheet H2 diagnostic comprising 3,360 trajectories (two Skill arms × three request seeds
× three repeats × 280 task instances), the paired Skill effect had a pooled within-seed repeat SD of 2.26
points and an estimated request-seed SD of 1.56 points; fixed-seed repeat variation accounted for 68% of the
estimated variance. This diagnostic is limited to one benchmark and two Skill arms, so it motivates repeated
execution but does not establish a universal variance decomposition.
Interaction tolerance.
The reported four-pattern prevalence uses a fixed descriptive tolerance 𝜖= 0.05
(five native-score points) applied to repeat-averaged four-cell contrasts. This threshold was not estimated
from A/A. A noise-qualified interaction analysis would additionally require a matched null for the four-cell
interaction contrast, not merely reuse a two-cell improvement tolerance. The existing prevalence therefore
characterizes thresholded response patterns rather than effects certified to exceed A/A noise.

B. Skill Provenance, Split Isolation, and Transfer Sensitivity
Construction and selection.
NoSkill supplies no learned artifact. Direct synthesizes a procedure once from
a frozen catalog, without rollout collection or a validation gate. SkillOpt uses training rollouts for iterative
edits, and locally generated Trace2Skill distills training-trajectory lessons under its recorded method-validation
procedure. The protocol reserves method validation for skill selection and separates harness qualification,
which qualifies execution code and interfaces rather than selecting skill content. Frozen packages are reused
Which Failure Does an Intervention Repair?
31
unchanged across target models instead of regenerated for each target. Holding the artifact fixed does not
remove its potential alignment to the construction model.
UID and artifact evidence.
The anonymized supplementary archive contains a provenance inventory
recording exact archived UIDs, split-file hashes, within-directory overlap checks, and saved freeze declarations,
together with the cross-model artifact bundle from which every frozen skill package is imported. UCSB
training and test UIDs come from the archived 280-item SOP split, whose original validation set is partitioned
into method and harness validation. LiveMath uses the archived ten-item method-validation split; Hotpot
stores its Context and FullWiki views beneath a common split root. The protocol excludes test instances from
generation, selection, patching, and acceptance. Disjoint UID lists and saved freeze declarations support
this rule but are not a complete audit of every historical generation call. Hash-freezing specifies unchanged
cross-model import; the inventory does not independently compare artifact bytes in every provider execution.
Spreadsheet.
SkillOpt and Trace2Skill both use the 80 training and 24 method-validation items.
Trace2Skill starts from the authors’ released initial skill bundle and runs the full evolution locally with
Qwen3.5-9B on these items (seed 42); the evolved xlsx/SKILL.md is the frozen artifact, and the two released
reference skills are carried over unchanged. The Direct catalog contains only the 80 training items: an
archived validation manifest lists 80 training plus 24 method-validation items, but the frozen generation
record and the prompt contain only the training items. The archived provenance records freeze entrypoints
and package hashes before evaluation.

We retain Sonnet 4.6, Sonnet 5, and GPT-5.6-sol on the same task instances

C.4 SimpleQA Knowledge Access
Design. If the bottleneck on SimpleQA is missing information, a skill built from the agent’s own data should
not help, a skill can at most make the model recognize the gap, and supplying the information should move
the score. We run Qwen3.5-9B under the paper’s H1 protocol (no browsing, skill in the fixed package block,

arms (Table 28). The search corpus contains, for each item, the source pages cited in its SimpleQA metadata
(293 of 300 items have text), split into 120-word chunks and retrieved with BM25. It therefore measures what
happens once the information is available, not the quality of open web search, and the external-knowledge
skill is an upper bound rather than a valid construction method. Δ is a paired item-bootstrap interval against
NoSkill.
Results. A skill built from the agent’s own data does not help. The knowledge-boundary skill replaces

Interpretation boundary.
The taxonomy localizes the earliest supported source error, whereas the matched
target outcomes indicate whether a tested intervention subsequently improves that case. The association does
not establish that the named root cause is the sole causal mediator, and labels produced from answer-only or
model-assisted evidence remain hypotheses. The transition analysis likewise describes replayed matched
executions; it does not constitute prospective continuation from one shared H1 state.

Recovery pathway.
Table 44 reports the Qwen3.5-9B H2 telemetry behind Section 4. Exposure is the share
of executions with an audited model-visible recovery signal; each later rate uses the preceding stage as its

Signal coding.
Each Qwen3.5-9B H1 failure is coded from its own H1 trajectory, before and independently
of the H2 outcome: an interface or contract violation (missing answer tag, premature or rejected final
submission), a runtime or tool error (execution error, invalid action, or tool-parameter error), or no error
signal (a wrong answer that raises nothing). Rescue is H2 success in the same instance, Skill, and repeat.
Pre-recovery diagnosis.
Among the 5,003 Qwen3.5-9B instance–Skill views that fail at H1 in a majority of
the three repeats, 14.1% succeed at H2 in a majority. A gradient-boosted classifier on H0 and H1 behavior
(outcome summaries, token and turn counts, tool use, premature submission, and the modal H1 failure type),
evaluated by five-fold cross-validation grouped by instance, ranks them with AUROC 0.945 and AUPRC
0.772, against 0.796 and 0.376 for benchmark identity alone (Figure 12; Table 46). Table 47 replays escalation

F. Routing Intervention Choice
F.1 Direct Routing
Every router has two stages. Stage A is the predictor: for each task and candidate action, a ridge regression
predicts whether the action beats the reference (Trace2Skill+H2 at Default budget), using only inputs
available before the outcome, under nested leave-one-benchmark-family-out cross-validation. Stage B picks
the action with the highest predicted gain, and its outcome and full call-chain token cost are replayed from the
saved runs.
The capability boundaries in Section D.6 leave headroom wherever several actions succeed. Whether that
headroom is usable depends on choosing the right action in advance, without first paying a probe to find out.
Table 48 compares five policies that must choose from the task text alone, under held-family historical replay.
Trace H1 and Trace H2 apply one harness level to every instance without routing. The Text+action Router
predicts the action directly from task text, whereas Text→root→action first predicts a root cause and then
maps that label to an action. The Observed per-instance Oracle picks the best action using matched outcomes
and is an unattainable reference. Every policy acts on Qwen3.5-9B, so ranking by mean full-chain tokens
ranks by cost.

F.3 Routing Results and Interpretation
Routing headroom exists, but deployable signals do not yet realize it.
Section 4 shows why routing could
matter: some failures admit several successful axes with different costs, while others require a particular
intervention. An Observed per-instance Oracle verifies that this heterogeneity contains substantial quality–cost
headroom. On the direct action set, it reaches 58.12% with 2,085 mean full-chain tokens, compared with
45.29% and 4,070 tokens for the Trace H2 reference. Thus, a policy that knew the matched outcomes could
be both more accurate and cheaper. The Oracle obtains that advantage by reading the target outcomes it is
supposed to predict, however, and is therefore an unattainable boundary rather than a deployable policy. Part
of its gap is also selection on noise, because it picks and scores the action on the same runs. Picking the
action on one repeat and scoring it on the other two leaves +3.95 points [+1.58, +6.36] over the reference
(49.24% versus 45.29%), which is our main estimate of direct-routing headroom.
The tested deployment-valid information paths do not realize this headroom. The H1-conditioned router
pays for an H1 probe before deciding whether to keep H1 or restart H2. It reaches 49.25% with 13,677 mean
full-chain tokens, whereas Always H2 reaches 51.01% with 10,243 tokens. This router has both lower quality
and higher cost and is therefore strictly dominated. Direct text-conditioned routing avoids the probe, but the
Text+action Router reaches only 39.42%, and Text→root→action reaches 40.10%, both below the 45.29%
Trace H2 reference. The latter also spends 4,264 tokens against 4,070 for Trace H2.
The result is a negative deployment finding rather than evidence that routing has no value: routing
headroom exists, but none of the tested lightweight deployable routing policies achieves a quality–cost Pareto
improvement. In the terms of Section 4,
failure information ⇏a cheap deployable decision signal.
These experiments are frozen historical replays rather than live prospective executions, and their money
and latency ledgers remain incomplete. We therefore make no positive routing claim. Instead, the gap
between the Observed Oracle and learned policies identifies the remaining problem: intervention selection is
a value-of-information problem in which acquiring the signal can consume the benefit of acting on it.

G. Benchmark Case Studies
This section reads the factorial results benchmark by benchmark. Task properties are the human-authored
design annotations in Table 14; trajectory roots use the eight operational definitions in Table 33. Root
frequencies refer only to the 2,225 labeled NoSkill+H1+Medium source failures in Table 19; they are not
benchmark labels, and the Hotpot estimates are too sparse for benchmark-wide interpretation. “Best” denotes
the largest observed three-repeat mean in the Default-budget matrix (Table 2). It is descriptive selection over
observed cells rather than a prospective policy.
G.1 SpreadsheetBench
Context, properties, and failures.
SpreadsheetBench requires stateful edits through a spreadsheet tool.
We therefore annotate high tool/state interaction and feedback demand, with Execution/tool as the expected
Which Failure Does an Intervention Repair?
54
bottleneck. The observed source labels agree: 587 of 588 labeled failures are Execution/tool, with one
Horizon/termination case. This unusually concentrated composition supports an execution interpretation for
this source condition, although it does not imply that every configuration fails for the same reason.
Best observed configuration and mechanism.
The best Default cell is Sonnet 4.6+NoSkill+H3 at 53.1.
The same Model rises from 48.6 at H0 to 49.2/51.1/53.1 under H1/H2/H3, while every supplied Skill lowers
its H3 score. Qwen shows a larger execution-support response: NoSkill rises from 9.3 at H1 to 24.9 at H2
and 30.4 at H3. The pattern is consistent with feedback, bounded repair, and revision addressing runtime
failures, while a frozen procedure can distract from the current workbook state.
Takeaway. Stateful spreadsheet work is primarily execution-limited in this matrix. A capable Model with
observable execution and revision is more useful than an additional frozen procedure, and Skill injection
should be treated as a possible source of interference.
G.2 LiveMathematicianBench
Context, properties, and failures.
LiveMath is a multiple-choice mathematical reasoning task with low tool
demand and a recurring meta-option. Its source labels are 73.44% Reasoning and 26.23% State/grounding,
both model-assisted hypotheses, plus 0.33% Procedural. The post-hoc meta-option partition in Appendix D.2.1
shows that a reusable answer-selection regularity exists inside the benchmark but does not cover all instances.
Best observed configuration and mechanism.
The best Default cell is GPT-5.6-sol+Trace2Skill+H1
at 62.1. For GPT-5.6-sol, Trace2Skill scores 61.6/62.1/57.8/60.5 across H0–H3; for Qwen it scores
53.2/58.1/56.5/54.6, far above Qwen+NoSkill at 34.1/34.9/34.4/36.3. In contrast, additional Harness support
is flat or non-monotone, and Sonnet 5+Trace2Skill declines from 40.6 at H0 to 35.5 at H3. The benefit
is therefore better explained by a reusable decision procedure plus model competence than by execution
recovery.
Takeaway. LiveMath rewards a reusable but narrow decision regularity. Trace-derived procedures help
broadly across observed contexts, yet subgroup reversal shows why the Skill should not be interpreted as a
general increase in mathematical capability.
G.3 UCSB SOPBench
Context, properties, and failures.
UCSB SOPBench requires following long, constraint-sensitive standard
operating procedures while interacting with state. We annotate high procedural and tool demand. Among
labeled source failures, 78.57% are Procedural, 13.91% State/grounding, and 7.52% Execution/tool, giving
the most direct root-level support for a procedure-oriented Skill hypothesis.
Best observed configuration and mechanism.
The best Default cell is GPT-5.6-sol+SkillOpt+H1 at
73.1, narrowly above H0 at 72.6; H2 and H3 fall to 71.6 and 70.3. Qwen shows the same Skill preference:
SkillOpt reaches 66.3 at H0/H1 versus 52.8/51.0 for NoSkill. Outcome-guided optimization can encode
ordering and verification constraints, whereas additional recovery or reflection is not uniformly useful once
that policy is supplied.
Takeaway. For procedure- and constraint-heavy SOP execution, an outcome-optimized reusable procedure
is the stable first intervention. Harness choice remains model-dependent and stronger recovery is not
automatically better after the procedure is supplied.

G.4 Amazon SOP
Context, properties, and failures.
Amazon SOP is a long, state-changing inspection workflow with high
procedure, tool, horizon, and feedback demand. All 113 labeled source failures are Execution/tool. Horizon
is nevertheless a task-level design hypothesis rather than an observed root conclusion, because the frozen
Medium-budget source cohort contains almost no labeled Horizon/termination failures.
Best observed configurations and mechanism.
The Default ceiling is 100.0 and is non-unique. It is reached
by Sonnet 4.6+NoSkill+H2, all four Harnesses with Sonnet 4.6+SkillOpt, Sonnet 4.6+Trace2Skill+H2,
GPT-5.6-sol+NoSkill+H2, and GPT-5.6-sol+SkillOpt+H2. The decisive transition is often execution
feasibility: Qwen+NoSkill rises 33.9→88.6 from H1 to H2, and GPT-5.6-sol+NoSkill rises 57.1→100.0. A
mismatched Skill can instead collapse the path: Qwen+Direct remains at 1.7 across H0–H3. The Low-to-best
Budget envelope is 81.13 points, consistent with a long workflow crossing a completion threshold rather than
smooth scaling.
Takeaway. Amazon SOP is governed by path feasibility and execution reliability. H2 or sufficient Budget
can unlock completion, but a mismatched procedure can prevent that path entirely; after feasibility is reached,
several configurations saturate at the ceiling.
G.5 SimpleQA
Context, properties, and failures.
SimpleQA asks for short factual answers without supplied evidence
or meaningful tool interaction. The labeled source failures are 74.84% Factual knowledge/recall, 24.78%
Abstention/calibration, and 0.38% Evaluation/answer contract; the first two categories are model-assisted
hypotheses. This composition aligns with a Model intervention more directly than with a procedural or
execution intervention.
Best observed configuration and mechanism.
The best Default cell is GPT-5.6-sol+NoSkill+H0 at 69.4.
GPT-5.6-sol remains near this level under H1–H3 (67.8/68.0/68.8), whereas Qwen+NoSkill is 10.7 at H0
and 4.7 at H2. Neither execution feedback nor a frozen procedure supplies a fact absent from the task and
not recalled by the Model. The within-axis Model span is 60.85 points, compared with Skill, Harness, and
Budget envelopes of 0.13, 0.00, and 0.10.
Takeaway. When the missing resource is factual recall, changing the Model dominates procedural and
execution support. SimpleQA is the clearest case in which additional Harness, Skill, or Budget mostly adds
cost without supplying the missing information.
G.6 SQuAD
Context, properties, and failures.
SQuAD supplies the evidence passage, so the primary challenge in this
setup is returning a creditable answer through the expected interface. All 159 labeled source failures are
Evaluation/answer contract. This is strong evidence for the audited source condition, but the native-score
floor analysis in Appendix A.6.1 means large H0→H1 gains should be read as contract specification rather
than reasoning recovery.
Best observed configuration and mechanism.
The best Default cell is Sonnet 5+Trace2Skill+H1 at 91.0,
followed closely by H2/H3 at 90.6/90.7. The interface transition is large: Qwen+NoSkill rises 10.7→36.6
from H0 to H1 and then 78.6/79.3 under H2/H3, while Sonnet 4.6+NoSkill rises from the 0.0 floor to 85.4 at
Which Failure Does an Intervention Repair?
56
H1. A Skill can partially supply an extraction/answer procedure at H0, but once the Harness specifies the
contract its incremental value is often absorbed.
Takeaway. SQuAD primarily tests whether the system exposes and satisfies the answer contract. H1
removes a measurement/interface bottleneck; after that transition, additional execution support or Skill often
has little incremental value.
G.7 HotpotQA Context
Context, properties, and failures.
Hotpot Context supplies gold and distractor paragraphs, reducing
retrieval demand while retaining multi-hop evidence integration. We annotate Evaluation/answer contract
as the expected bottleneck. Only one source failure is labeled, also as Evaluation/answer contract, so root
composition cannot explain the benchmark; this is a coverage limitation rather than confirming evidence.
Best observed configuration and mechanism.
The best Default cell is Sonnet 4.6+Direct+H3 at 69.2.
The main transition is H0→H1: that configuration rises 16.6→66.8, and Sonnet 4.6+NoSkill rises 0.0→66.2.
Later Harness levels add little. Skill compatibility remains important: GPT-5.6-sol+SkillOpt stays at
0.0/13.6/12.2/12.2, compared with 29.7/64.6/64.3/60.9 for Direct. The former is consistent with a supplied
policy overriding the answer contract, not with a graded loss of reasoning ability.
Takeaway. When evidence is already provided, interface compatibility dominates retrieval support. H1
captures most of the observed gain, and an incompatible Skill can erase it; the sparse root labels do not
support a benchmark-wide mechanistic claim.
G.8 HotpotQA FullWiki
Context, properties, and failures.
Hotpot FullWiki uses the same question UIDs as Context but removes
the supplied passages and permits retrieval from a frozen Wikipedia index. This creates multi-hop search,
grounding, execution, and horizon demands. All ten labeled source failures are Execution/tool, but ten labels
are far too few to characterize the benchmark because missingness is concentrated in the Hotpot views.
Best observed configuration and mechanism.
The best Default cell is Sonnet 5+Trace2Skill+H1 at 45.0,
compared with 30.9 for Sonnet 5+NoSkill at H1. Qwen reveals the interaction mechanism: Direct rises
from 3.9 at H1 to 28.4 at H2, SkillOpt from 24.0 to 34.9, and Trace2Skill from 34.1 to 36.0. A reusable
retrieval policy supplies what to search and how to integrate evidence; executable observations and recovery
determine whether weaker configurations can carry out that policy. The strongest cell nevertheless uses H1,
showing that more recovery is not universally necessary once Model and Skill are well matched.
Takeaway. FullWiki couples a reusable multi-hop retrieval policy with the ability to execute it. Trace2Skill
is the stable Skill choice in the observed matrix, while Harness support is most valuable when the current
Model–Skill pair cannot reliably realize that policy.
G.9 BigCodeBench
Context, properties, and evidence boundary.
BigCodeBench-Hard requires program synthesis and
execution against evaluator-private tests. We annotate medium procedural and horizon demand, high tool
interaction and feedback demand, and Execution/tool as the expected bottleneck. We use all 148 available
instances across frozen construction, validation, qualification, and test roles (Table 16).
Which Failure Does an Intervention Repair?
57
Why no comparable winner is reported.
BigCode is retained as supporting appendix evidence because
its evaluator environment is not fully comparable across Models. It is therefore excluded from the 512-cell
Table 2 and the root-conditioned common-support cohort. Reporting a cross-model “best intervention
combination” from those analyses would silently mix evaluator differences with intervention effects.
Interpretation.
The task structure motivates executable feedback and Model capability as hypotheses, but
the present evidence cannot distinguish them on the same matched scale used for the other eight benchmarks.
A valid case analysis requires rerunning every Model under one frozen execution image, scorer, dependency
set, timeout policy, and task split, followed by the same three-repeat factorial and root-label protocol.
Takeaway. Code execution is a plausible feedback-sensitive setting, but evaluator comparability is a
prerequisite for attributing gains to Model, Skill, Harness, or Budget. BigCode remains supporting evidence
rather than a ninth point in the comparative mechanism claims.
G.10 Cross-Case Synthesis
The cases separate four recurring structures without turning them into universal rules: missing factual
